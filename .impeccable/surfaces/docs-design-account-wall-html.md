# 账号矩阵 · 本地 Web 首页

- **Scope**：`localhost:8787` 首页，1440 桌面与 390 手机同页两态。
- **Mode**：Operate。
- **Audience**：P1 独立创作者 / 一人公司，同时运营多个账号组，每组跨多个平台。
- **Job**：先处理待办，再借矩阵确认全局健康；两条路径都通到同一个详情。
- **Action**：重新登录、续期、放行发布、查看账号；全局主动作是发布内容。
- **Proof / Content**：登录状态、最近发布结果与时间、最近采集结果与时间、失败原因、最近成功时间。
- **Constraints**：行是账号组，列是平台；每组每平台最多一个账号；中文为主；不抄 Postiz 的紫+黑；只用系统字体；无框架；手机同页折叠。

## Direction contract

**THESIS**：首页是「待办直达 + 账号组 × 平台健康矩阵」的双路径：待处理事项一眼可点，矩阵负责全局定位与缺口暴露。拒绝把正常账号与异常账号做成同一视觉层级，也拒绝详情沉底、让用户点完格子找不到反馈。

**OWN-WORLD**：深海军蓝 `#16324f` 的常驻导航与全局发布按钮，冷灰白 `#f4f4f2` 场地，白色矩阵，墨黑正文；正常态只有绿点灰绿字，琥珀 / 红浅底签只给异常；时间与数字等宽。没有航空术语或造型。

**STORY**：用户进来先看到「2 个登录异常 · 1 条发布待放行」与三个待办文字链 → 点“小红书重登”直达该格，详情在 AI 工具研究所行下方原位展开：handle 主标题、一句异常结论（含最近成功时间）、发布/采集两列证据、唯一主按钮“重新登录” → 处理完点“抖音续期”或任意格，详情跟随移动，行列坐标同步加重。

**FIRST VIEWPORT**：桌面左侧 224px 深蓝导航（品牌 / 发布内容 / 四项导航 / 本地承诺）；主区依次为「账号矩阵」标题与口径化摘要、待处理条 + 登录检查时间、2×5 矩阵（每格：登录状态 / 发布结果·时间 / 采集结果·时间）、选中账号组的组内详情行。未接入格保留缺口与预填上下文的添加入口。手机 ≤900 每个账号组变成一段卡片，平台逐行排布，详情紧跟当前组。

**FORM**：由用户明确的二维业务模型直接指定；基数与 Metricool Brand、Later Social Set 的“每组每平台一个账号”一致，首页采用竞品公开资料中未见到的健康矩阵主视图；待办直达与组内详情为本轮产品经理评审加入。seed: seed:a61cb2af8194ee80（历史引用；当前形式由用户业务模型覆盖）

**FINISH**：unreviewed and undocumented is unfinished; this build ends with the finish review, the verdict, DESIGN.md, and every shipping raster carrying its provenance.

## Workspace model（用户反馈后修正）

用户指出：分了多个账号组，用户一次只管理一个组，切组应有独立入口。据此把账号组从「分组标签」改成**全局工作上下文**：

- 入口 `groups.html`：首次进入选组或建组；之后记住上次选择（localStorage）。
- 侧栏常驻切换器，切换后所有页面同步换组；另有两项只读跨组视图。
- `account-wall.html` 只服务当前组：五个平台槽位，接入的显示状态，未接入的显示缺口与添加入口。
- `matrix.html`：跨组矩阵，只读，点格进入对应组。
- `add.html`：添加账号/重新登录，组已锁定，支持 `?platform=` 与 `?mode=reauth` 预填。
- 发布、作品、总览、任务均按当前组过滤；总览另有 `?group=all` 跨组汇总。

## Prototype scope (after this surface)

用户要求把完整产品原型做完。五页同源：

- `account-wall.html` 账号矩阵（本契约文件的主目标）
- `publish.html` 发布台：**写一条**（选账号、逐平台差异字段、预演、发布）与**发布计划**（周/月/列表三视图，作品卡为单位，可改期与取消）两种模式
- `work.html` 作品详情：跨平台并排、趋势与缺口、采集现场
- `overview.html` 总览：时间范围、平台拆分、数据新鲜度
- `runs.html` 任务与日志：队列、失败现场、重试

共用 `app.css`（token + 外壳 + 通用组件）。五页互相可达，每页露出等价的 `vk` 命令，落实 CLI 完整律。

## Resolved after user review

- 账号组是查看、选择与聚合维度，不是新的发布对象；发布仍指向具体平台账号。
- 每组每个平台最多一个账号，因此单元格不需要聚合多个账号。
- 状态口径统一为三条线：登录状态（正常/将过期/已失效）、发布结果（成功/失败/待放行）、采集结果（成功/失败 + 距今）；“登录正常”不等于“没有待办”，TikTok 待放行走发布事项，不改写登录状态，也不计入登录异常数。
- 格内时间必须绑定结果，失败与数据陈旧不靠点进去才发现。
- 详情以 handle 为主标题、“账号组 · 平台”为定位小字；不重播矩阵已有的状态签；正常账号不写空话。
- 详情主按钮指向具体对象与不同链接（reauth / renew / release / detail），不只换文案。
- 空格“添加”预填账号组与平台；页头通用添加先选组再选可用平台。
- 手机不隐藏正常账号，改为按账号组分段；详情就近展开并滚动到可见。
- 删除页面级复读：操作教学句、侧栏与页脚重复的凭证承诺（窄屏侧栏隐藏时页脚才显示）、重复的检查时间。

## 小红书扫码登录（#101，2026-11-14）

- **为谁**：账号页上小红书账号「已失效 / 即将过期」的创作者，人在电脑前、手机在手边。
- **解决什么**：原来「重新登录」只会弹出一个新的 Chrome 窗口让人在里面登录，打断手上的事，还要回到页面确认；创作服务平台现在支持「APP扫一扫登录」。
- **成功长什么样**：点「重新登录」→ 详情面板里直接出现二维码（后台无头 Chrome 取自创作平台登录页，屏幕上不出现新的浏览器窗口）→ 手机扫码 → 显示「已扫码，请在手机上确认登录」→ 手机确认 → 页面不刷新自己变成「正常」（login.status=ok 之后再跑一次 account.check 复核）。二维码过期自动换新；换不了时明确说「已过期」并给「刷新二维码」。
- **明确不做**：不改其他平台的登录方式（B站仍是自己的扫码窗口）；不在页面里展示或读取任何 cookie；不自动重试短信；不把「打开了二维码」当成「登录完成」。
- **数据从哪来**：`POST /api/accounts/:id/login/qr`（account.login.qr，返回二维码 data URL）→ 每 2 秒 `POST /api/accounts/:id/login/status`（waiting / scanned / expired / pending / ok / failed）→ `POST /api/accounts/:id/check`。备用入口：`login/start` + `login/verify`（短信验证码）、`login/open`（打开登录窗口，沿用原有等待确认流程）。
- **结构**：二维码面板挂在当前账号的详情里（一页一个任务：处理这个账号），不另开页面、不弹层；左边二维码，右边一句状态 + 「刷新二维码 / 取消登录」，下面一条分隔线后是备用入口「短信验证码登录 / 打开登录窗口」。手机 ≤900 上下堆叠，二维码居中，按钮至少 40px。
- **状态词表**：正在取二维码… · 等待扫码 · 已扫码，请在手机上确认登录 · 二维码过期了，已自动换成新的 · 二维码已过期（刷新） · 小红书拦下了这次扫码登录（风控，给备用入口） · 扫码登录页面变了样（给备用入口） · 重新登录完成。
- **等价命令**：`vk account login <id> --qr`（输出二维码图片路径并等待到成功或过期）；备用 `--phone <手机号>` / `--code <验证码>` / `--open`。
