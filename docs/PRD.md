## 0. 一句话

> **Claude 做完的内容，进库、一次发到各平台、看懂数据；手机上拍板。**

versekit 首先是作者自己（一人公司）的工具，开源，以后可以分享给同样用 AI 做内容的人。它不做内容，内容在 Claude 里做；它管内容做完之后的一切：放哪、发哪、发得怎么样、为什么。

## 1. 用户与场景

### 1.1 用户

**P1：作者自己**（所有取舍以此为准）
- 一人公司，用 Claude Code 做视频、图文和文章。
- 8 个发布目标：小红书、抖音、视频号、B站、TikTok、YouTube、官网（assurelane.ai）、公众号（订阅号）。每个平台 1 个账号。
- 三台设备：英国的 Mac mini 做内容（也是开发机）；和手机同网的 Mac 负责发布，常开；手机上用飞书。另有一台国内云服务器 volc1。
- 不在电脑前的时间远多于在电脑前。

**P2：以后的分享对象**：同样用 AI 做内容的个人创作者。多数在国内，用 Windows，没有服务器。所以**单机模式是默认**，分布式只是配置（ADR-0003）。

不服务：团队、矩阵号运营、代运营。

### 1.2 作者的一天（目标形态）

1. 上午在 Mac mini 上用 Claude 做完一期视频：竖屏中文版、横屏英文版、封面、口播稿。Claude 最后一步调 versekit skill，**这一期作为一个作品入库**。
2. 云端按平台改写标题、文案、话题，排进发布计划。手机上收到飞书卡片："新作品《…》已入库，建议发 6 个平台"。
3. 在手机上点开，看视频、看每个平台的标题，改一两处，点**确认**。小红书单独再点一次。
4. 发布机按排期和平台规则逐个发出，发完回读确认。哪个失败了，飞书上告诉你原因和能点的按钮。
5. 第二天早上飞书日报：昨天发的作品各平台数据，哪条比平时好、哪条差，**为什么**。
6. 周末看一次周报：这周哪类选题、哪个平台、什么时间段表现最好，下周做什么。

### 1.3 要解决的问题（按痛感排序）

| 问题 | 现在 | versekit 之后 |
|---|---|---|
| **内容没处放** | Claude 做完的成片散落在各个仓库目录里，哪些发了、发在哪，全靠记 | 做完即入库；一个作品库看到每条内容在各平台的状态 |
| **发不动** | 8 个平台逐个打开、逐个改标题话题、逐个上传；工厂能自动发几个，但只能作者自己在一台机器上用 | 一次确认，按平台改写好的内容自动发出 |
| **不知道为什么爆** | 各平台后台分别看，数字不可比；爆了没爆都说不出原因 | 数据回到一处，按"同账号同发布时长"的基线比较，LLM 给出带证据的原因 |
| **怕被封** | 11-14 小红书号因异地 IP 加短时多次自动发帖被处罚 | 按平台规则发（频率、间隔、AI 标识、熔断）；账号绑定和手机同网的发布机 |
| **离开电脑就卡住** | 登录过期、发布失败要回到电脑前才知道 | 飞书先告诉你，能在手机上处理的直接处理 |

## 2. 不做

| 不做 | 为什么 |
|---|---|
| 内容生产（写稿、出片、配音、剪辑） | 在 Claude 里做；versekit 只接收成品 |
| 公开内容采集、竞品监控 | 法律风险，且是另一个产品 |
| 团队、权限、审批流、矩阵批量 | 自用，一个人拍板 |
| 托管 SaaS、替别人保管账号 | 凭证永不离开发布机（BLUEPRINT D6） |
| 评论、私信回复 | 和"发布 + 数据"主线不同 |
| 逆向平台签名接口 | 只用官方接口，或用户自己登录后页面发出的请求 |
| 和蚁小二比平台数量 | 平台覆盖够自己用就行，控制面才是重点 |

## 3. 产品对象

产品的中心是**作品**，不是账号。所有页面、卡片、命令都从作品出发。

```
作品 work（一期内容）
  └── 成片 cut（一期里的一个剪辑：长片、短片 1/2/3、文章。同一支成片可以有几个语言版本）
        ├── 素材 asset（这支成片的文件：各语言版本的横屏、竖屏、各比例封面、字幕、正文）
        └── 平台稿 publish（这支成片的某个语言版本发到一个平台的一条：标题、文案、话题、封面、可见性、排期）
              ├── 发布记录 run（每次尝试：成功、失败原因、截图）
              └── 数据快照 snapshot（+1h、+6h、+24h、+3d、+7d、之后每天）

同一个平台在一期里可以有多条平台稿（例如小红书：长片 1 条 + 短片 3 条，分几天发）。

账号 account：平台 + 昵称 + 登录状态 + 绑定的发布机
发布方案 plan：哪种成片、哪个语言版本发到哪些平台，按什么节奏（每个人自己的习惯，可改）
分析 insight：针对一个平台稿、一个作品或一段时间的结论（带证据、带生成时间）
```

| 对象 | 用户看到的名字 | 关键字段 | 说明 |
|---|---|---|---|
| work | 作品 | 标题、类型（视频 / 图文 / 文章）、选题标签、`ai_generated`、来源（哪个仓库、哪次提交）、入库时间、备注 | 一期内容就是一个作品，不管有几个版本 |
| cut | 成片 | 名称（入库时带进来，可以不起）、类型（长片 / 短片 / 文章）、时长、语言版本 | 成片按剪辑分，语言是版本，不是另一支成片。作者自己一期通常 4 支：长片 + 3 支短片，每支有中文和 English 两个版本。最简单的作品只有 1 支成片、1 个版本。平台稿挂在成片下，不直接挂在作品下 |
| asset | 素材 | 种类（视频 / 封面 / 图片 / 正文 / 字幕）、语言、画幅、时长、sha256 | 文件按哈希存放（ADR-0003 §2.5） |
| publish | 平台稿 | 所属成片、语言版本、平台、账号、所用素材、标题、文案、话题、封面、可见性、排期时间、状态 | 改写结果落在这里，人可以改 |
| plan | 发布方案 | 成片类型 + 语言版本 → 平台列表、节奏 | 入库时按它生成平台稿和建议时间；默认方案是"每支成片发到所有已接入的平台" |
| snapshot | 数据 | 采集时间、指标（播放、点赞、评论、收藏、分享、完播等，按平台不同）、来源、是否完整 | 指标用键值存，各平台不同 |
| account | 账号 | 平台、昵称、登录状态、绑定发布机、发布后端 | 每个平台一个号 |
| insight | 分析 | 对象、结论、证据（引用哪些数字）、模型、生成时间 | 可以重新生成，旧的保留 |

### 3.1 通用性（2026-11-15 定）

模型的每一层都是"一个或多个"，界面按数量收放，不为作者自己的习惯写死：

| 层 | 作者自己 | 只发一条视频的人 | 界面 |
|---|---|---|---|
| 作品 → 成片 | 4 支 | 1 支 | 只有 1 支时不出现成片列表 |
| 成片 → 语言版本 | 中文、English | 1 个 | 只有 1 个时不出现语言切换 |
| 成片 → 平台 | 7–8 个 | 2–3 个 | 平台来自这个人接入了哪些账号 |

属于个人习惯、必须做成配置的：成片的名字、发布方案（哪支发哪些平台）、排期节奏、"好"和"差"的阈值。
属于平台规则、对所有人一样的：没确认不发、小红书逐条确认、每日上限与最小间隔、AI 标注。
原型里用 `#demo=simple` 可以换成"一条视频、一种语言、三个平台"的示例验证。

**作品状态**由平台稿推出，用户不手动改：

| 作品状态 | 条件 |
|---|---|
| 未编排 | 入库了，还没有平台稿 |
| 待确认 | 有平台稿，还没确认 |
| 排期中 | 已确认，有平台稿在等排期时间 |
| 发布中 | 有平台稿正在发 |
| 已发布 | 所有平台稿都终结，且全部成功 |
| 部分完成 | 所有平台稿都终结，有失败、有待人处理、或有后置动作没完成 |

**平台稿状态**沿用现有状态机（BLUEPRINT §2.4、§2.6）：草稿 → 待确认 → 排期中 → 发布中 → 已发布 / 已发布但受限（有后置动作）/ 待人处理 / 失败（带原因）。**每条平台稿必须终结在一个明确状态，静默失败是 P0 缺陷。**

## 4. 核心流程

### 4.1 入库（Claude → versekit）

- 入口是 **Claude Code skill**（`versekit-ingest`）和 CLI `hifabu work add`。skill 只是帮 Claude 调 CLI，不另写逻辑。
- 最简形式：`hifabu work add 视频.mp4`，一个文件就是一个作品、一支成片、一个版本。多支成片、多语言是它的完整形式。
- 入库内容：作品标题、类型、全部素材文件、口播稿或正文、选题标签、`ai_generated`、来源仓库和提交、给发布用的提示（例如"这期适合 B站长视频"）。
- 同一个作品重复入库（同一来源、同一标题）时更新，不新建；素材按哈希去重。
- 入库后推飞书卡片"新作品已入库"，带"去编排"按钮。
- 在制作机上入库，文件上传到云端（分布式）或留在本机（单机）。

### 4.2 编排（一次编排，按平台改写）

- 目标平台来自**发布方案**：入库时按方案给每支成片的每个语言版本生成平台稿；没设过方案就是"每支成片发到所有已接入的平台"。可以在某个作品上临时增减。
- 各平台的标题、文案、话题**在入库时由 Claude 写好**（所有者 2026-11-16 定），随清单交给 `hifabu work add`，versekit 本身不接 LLM 做改写；入库时按平台字段限制校验（`research/platform-rules.md` 第三节），确认时人可以看、可以改。提示"这是 AI 生成的内容，会按平台要求标注"。
- 每个平台稿默认选好素材：竖屏给小红书、抖音、视频号、TikTok；横屏给 B站、YouTube、官网；文章给公众号。可以改。
- 排期：按平台规则（每日上限、最小间隔）和"这个账号历史上表现好的时段"给建议时间；冲突的自动顺延并说明原因。
- **没有人确认，任何一条都不会发出去。**（2026-11-15 用户定）改写和排期只是建议；每条平台稿要么由人确认"按这个时间发"，要么由人点"现在发"，要么标成"我自己手动发"。没确认的到了建议时间也不发，只提醒。
- 确认按成片进行：看一遍这支成片，一次确认它下面的几条平台稿（这是人看过之后的同意，不算自动）。**小红书的平台稿必须逐条单独确认**，不能被批量确认带上。
- 确认之后的执行（上传、填文案、回读）是自动的；BLUEPRINT §2.4 的 `auto` 模式指的是这一段。
- 确认前能在手机上看视频：机器人把这支成片的预览版作为视频消息发到飞书。

### 4.3 发布

- 发布机按排期领取任务（ADR-0003 §2.3），按账号选后端：官方接口 > 自研浏览器自动化 > SAU（BLUEPRINT §2.1）。
- 发布前检查：账号登录状态、当天额度、最小间隔、AI 标识、字段长度。不满足就顺延或报错，并说明原因。
- 发布后回读确认拿到作品链接；拿不到的平台标为"待人确认"，推卡片让人点"我已看到"。
- 失败：推卡片，给原因和按钮（重试 / 改成手动 / 看截图）。平台返回封禁、限流、验证码、要求重新登录时，**该账号暂停全部自动操作**，不自动重试。
- 后置动作（B站合集、YouTube 可见性等）系统自己核实，核实不了才找人。
- 各平台的特殊处理：

| 平台 | 默认后端 | 特殊规则 |
|---|---|---|
| 小红书 | 自研浏览器自动化 | 只在发布机上跑；每条手机确认；每天 ≤ 1 条（建议值，可改） |
| 抖音 | SAU，`video.create.bind` 获批后切官方接口（#130） | |
| 视频号 | SAU | 没有个人可用的官方接口 |
| B站 | 自研（biliup） | 合集归属作为后置动作核实 |
| TikTok | 自研浏览器自动化，审核通过后切官方接口（#143） | 隐私级别手选、互动开关默认关、`is_aigc` |
| YouTube | 官方接口 | 在发布机上跑（volc1 连不上）；`containsSyntheticMedia` |
| 公众号 | 官方接口 `draft/add` | 只推到草稿箱，人在手机上点发表；在云端跑（固定 IP 白名单） |
| 官网 | trustbridge 仓库的站点脚本 | 在制作机上跑 |

### 4.4 数据与分析

**采集**：发布后 +1h、+6h、+24h、+3d、+7d，之后每天，最多 30 天。每次记录来源和是否完整；连续两次失败推卡片。

**比较的口径**（"好"和"差"必须可比，否则分析没有意义）：
- 同一账号、同一发布时长比较。例如"发布 24 小时的播放"只和这个账号其他作品"发布 24 小时的播放"比。
- 基线 = 这个账号最近 20 条的中位数。高于 2 倍算"爆"，低于 0.5 倍算"扑"，都可以改。
- 新账号或历史少于 5 条时，不下结论，只展示数字。

**分析的三个层次**：

| 层次 | 什么时候生成 | 回答什么 | 出现在哪 |
|---|---|---|---|
| 单条 | 平台稿发布 24 小时、7 天后 | 这条比平时好还是差，可能因为什么（标题、封面、发布时间、时长、选题、平台推荐流量占比） | 作品详情；飞书日报 |
| 作品 | 所有平台稿发布 7 天后 | 同一内容在哪个平台最好，为什么 | 作品详情 |
| 周报 | 每周一早上 | 这周哪类选题、平台、时段最好；下周建议做什么 | 数据页；飞书周报 |

**分析的规则**：
- 每条结论必须引用具体数字（"播放 3.2 万，是基线的 2.4 倍"），不写空话。
- 区分"数据说明的"和"推测的"，推测要标出来。
- 可以重新生成，旧结论保留，带模型和时间。
- 用云端 LLM（OpenAI 兼容接口，默认火山方舟，BLUEPRINT D12）。没配 LLM 时只展示数字和基线比较，不报错。

### 4.5 账号健康

- 每个账号显示登录状态、上次检查时间、绑定的发布机、今天还能发几条。
- 登录快过期、已过期、被限流时推卡片。扫码登录时，发布机把二维码传到云端，**手机飞书里直接显示二维码**，用另一台设备扫，或在发布机前扫（ADR-0003 §2.6）。
- 开发机不能绑定国内平台账号（真机红线）。

### 4.6 手机上拍板（只用飞书）

**手机上只有飞书**（2026-11-15 用户定）：不做手机网页，不做 App。看视频靠机器人发的视频消息，确认、改标题和时间、处理失败都在飞书卡片里完成（卡片表单、时间选择器、原地更新）。完整数据和细致编排在桌面 Web。具体做法见 `docs/design/FLOW-v2.md`。

飞书卡片清单（8 张）：

| 卡片 | 什么时候推 | 按钮（≤ 3 个） |
|---|---|---|
| 新作品入库 | 入库后 | 去编排 · 稍后 |
| 待确认 | 编排完成 | 打开确认（卡片上不能直接批量发） |
| 小红书确认 | 每条小红书平台稿 | 确认发布 · 打开看 · 不发 |
| 发布结果 | 一个作品的平台稿全部终结后，合成一张 | 打开作品 ·（有失败时）全部重试 |
| 发布失败 / 账号暂停 | 立即 | 重试 · 改成手动 · 看截图 |
| 需要登录 | 登录过期或被要求验证 | 显示二维码 · 我已处理 |
| 发布机离线 | 到了排期时间发布机仍不在线 | 我知道了 · 改期 |
| 结果摘要 | 有新结果才发：有平台稿满 24 小时，或有一条明显高于、低于基线（可关） | 打开作品 |
| 周报 | 每周一 9:00（可关） | 打开周报 |

卡片规则：一句话结论在前；只放做决定需要的信息；不放日志、路径、凭证；点完在原卡片上更新结果，不刷屏；按钮 24 小时过期。

## 5. 界面

### 5.1 四个入口的分工

| 入口 | 给谁 | 做什么 |
|---|---|---|
| CLI `hifabu` | Claude、脚本 | 全部能力，JSON 输出。任何能力先在 CLI 上存在（CLI 完整律） |
| Claude Code skill | Claude | 入库、查状态、查数据，让 Claude 做下一期时能参考上一期的表现 |
| Web（桌面） | 坐在电脑前的作者 | 编排、看数据、管账号、排障 |
| Web（手机）+ 飞书 | 不在电脑前的作者 | 看作品、确认、处理失败、看日报周报 |

### 5.2 页面清单（原型就做这些）

一个人用的工具，4 页。只按桌面设计；手机上不开网页，全部走飞书。

| # | 页面 | 一句话职责 | 里程碑 |
|---|---|---|---|
| 1 | **今天**（首页） | 现在要我做什么：待确认的成片、出问题的、接下来 48 小时要发的；再往下是最近结果（和基线比） | M1 起，逐步补全 |
| 2 | **作品** | 档案：所有作品；点进去是作品详情（成片、各平台稿状态与链接、数据、分析）；确认页也从这里进 | M1（数据部分 M4） |
| 3 | **数据** | 各平台、各选题、各时段对比；周报 | M4 |
| 4 | **系统** | 账号登录状态与今日额度、设备在线状态、任务与日志；扫码登录 | 已有页面合并，M2 加设备 |

**确认**是最重要的流程，手机上是飞书里的"视频消息 + 确认卡片"，桌面上是确认页：一期 → 逐支成片 → 这支成片的各平台稿（标题、时间可改）→ 确认。发布计划不单独成页：接下来要发的显示在"今天"。

另有**飞书卡片**一组（§4.6），和页面一起出原型。**原型顺序**：飞书卡片和手机确认页 → 今天 → 作品详情 → 数据 → 系统。

旧原型（`docs/design/`）全部作废，包括账号组、矩阵、发布台、总览。

### 5.3 设计原则

- **先说要我做什么**：首页是"今天"；所有通知都能一跳到对应作品或确认页。
- **数字和基线比**：主要信息是"基线的几倍"，原始播放数是次要信息；不同平台的播放数不相加。
- **封面是主角**：作品用真实封面表示，界面本身保持安静；一个强调色只表示"等你处理"，红色只表示失败。
- **"决定"类操作在飞书里就能做完**：确认、重试、显示二维码都是卡片上的按钮，单手可以完成。
- **数字带口径**：每个数字旁边写清"发布多久时""和什么比"。
- **说人话**：错误、原因、分析都写成一句能直接行动的中文，不出现错误码以外的技术词。

## 8. 非功能需求

- **安全**：凭证只在发布机，云端和卡片里都没有；设备令牌按角色限权、可吊销；云端 Web 要登录、防爆破。
- **隐私**：不发遥测；内容和数据只在用户自己的机器和服务器上；LLM 只收到改写或分析需要的字段。
- **韧性**：任何一台机器掉线不丢任务；发布机离线时账号任务不改派，推卡片；云端挂了，发布机已领的任务做完后暂停。
- **可观测**：`hifabu doctor` 能看出每台设备、每个账号、每个通道的状态；每次失败都有原因、截图和事件。
- **平台**：macOS 优先；分享给别人之前要支持 Windows 单机模式。
- **性能**：作品库 500 个作品、手机 4G 网络下首屏 < 2 秒；视频在手机上能边下边播。

## 9. 成功指标

自用阶段不看安装量，看作者自己的时间和账号安全。

| 指标 | 目标 |
|---|---|
| **北极星**：每周从入库到全部平台终结的作品数 | 追踪，不设目标 |
| 一期（约 4 支成片、22 条平台稿）从入库到全部确认的人工时间 | < 5 分钟（不含看片） |
| 作者需要回到电脑前处理的次数 | 每周 < 2 次 |
| 账号因 versekit 的操作被平台处罚 | 0，出现一次即 P0 |
| 静默失败 | 0，出现一次即 P0 |
| 分析结论被作者认为"有用" | 每周反馈，持续改提示词 |

## 10. 风险

| 风险 | 应对 |
|---|---|
| 平台改版导致自动化失效 | 能走官方接口就走；适配器独立；失败截图 + 卡片 |
| 浏览器自动化违反国内平台协议（`platform-rules.md` 第一节） | 频率保守、和手机同网、小红书逐条人工确认；官方接口获批后切换 |
| LLM 分析说空话或编造 | 必须引用数字；区分事实和推测；作者每周反馈 |
| volc1 出口带宽窄（下载约 0.11MB/s） | 预取；必要时换对象存储（ADR-0003 §2.5） |
| 做成只有作者能用的脚本 | 单机模式默认、配置不写死、移植时剥离硬编码（ADR-0001） |
