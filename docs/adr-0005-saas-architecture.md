# ADR-0005：做成 SaaS 的研发架构（数据、隔离、设备、文件、升级）

**状态**：提议（2026-11-18；2026-11-22 修订：做客户端、先验证本机制作和发布、对象存储暂缓，见 §15 第 7–9 条；2026-11-24 修订：先做最小账号，见 §15 第 10–13 条）　**决策人**：产品 + Claude
**前置**：[ADR-0003](adr-0003-distributed.md)（云端 + 制作机 + 发布机）、[ADR-0004](adr-0004-multi-user.md)（多用户）。两篇仍是「提议」，本篇和它们一起评审。
**修订**：ADR-0004 §2.2（隔离做法）、§2.3（进来的方式）、§2.4（加设备的流程）；ADR-0003 §2.5（文件）、§2.7（鉴权）；BLUEPRINT §1.5、§3.1、D11；PRODUCT.md 原则 5
**影响**：表结构、鉴权、文件存储、发布机安装与升级、Claude 接入、所有页面（界面不再出现命令）

---

## 1. 背景

所有者 2026-11-18 定的方向：

1. versekit 要做成 SaaS：别人登录到同一个服务来用，用户之间不能串。
2. 用户的所有操作都在界面上完成，包括升级、登录平台账号。界面上不出现命令行。
3. 制作机做完视频后的上传、发布机的下载都在后台自动进行，不出现命令。
4. 发布机要让用户看得到当前的出口 IP 和所在的国家、城市。
5. 以后的验收要在研发架构上把关。

不变的约束：

- 平台账号只能在和手机同网的电脑上操作（11-14 小红书处罚的根因）。云端永远不替任何用户发布，平台登录永远不离开用户的发布机（BLUEPRINT D6）。
- 三条铁律：CLI 完整律、三端一致律、零后门律。
- 无运行时依赖（Node 内置的 `node:sqlite`、`node:crypto`、`fetch`、`WebSocket`）。
- 没有人确认，一条都不会发。

### 1.1 量级假设

选型按这组数字做，超出时按 §3.5 的条件重新评估。

| 项 | 现在 | 设计目标 | 说明 |

| 用户 | 2 | 500 | 邀请制起步 |
| 每个用户每周的平台稿 | 约 25 | 100 | 所有者自己：一期 4 支成片、22 条 |

## 2. 决策一览

| # | 问题 | 结论 |
|---|---|---|
| A1 | 数据库 | 继续用 SQLite。**每个用户一个库文件**，另有一个控制库放用户、会话、设备 |
| A2 | 隔离 | 由「拿到哪个库」保证，不靠每条查询带用户条件。命令拿到的句柄只能读写当前用户的库 |
| A3 | 文件 | **暂缓**（§15 第 8 条）。默认一台电脑上制作和发布，不用中转；分机只给所有者自己用，沿用现有 `packages/relay`。对象存储方案保留在 §4，等真有多个用户要分机再做 |
| A4 | 人的登录 | **Google 登录和邮箱验证码登录，不设密码**（§15 第 11 条，取代邮箱 + 密码和邀请码）。会话放 HttpOnly cookie；注册开放 |
| A5 | 设备的登录 | 设备码配对：设备显示一个码，用户在网页上点「允许」。令牌属于一个用户、一个角色 |
| A6 | 客户端 | **做成客户端**（§15 第 7 条）：一台电脑装上就能制作和发布。测试阶段不签名，公开发布前必须签名。装完是后台服务，自己升级；分机时自己配对、领活、取文件 |
| A7 | Claude 接入 | **plugin**（技能 + 本机 MCP 服务），不是单独的 skill |
| A8 | 界面与命令 | 命令仍只在 `commands.mjs` 定义一次，多派生一端（MCP 工具）。界面上不显示命令 |
| A9 | 出口位置 | 发布机用账号的浏览器探测出口 IP；位置在云端查离线库。和账号平时的位置不一样时，暂停这个账号的自动发布 |
| A10 | 升级 | 云端由运营升级；发布机自动升级，界面上有「现在更新」；协议带版本号，云端兼容前一个版本 |

## 3. 数据库（A1、A2）

### 3.1 比较过的三种做法

| | 共用一个 SQLite 库，每张表加 `user_id` | **每个用户一个 SQLite 库** | PostgreSQL + 行级安全 |
|---|---|---|---|
| 串数据的可能 | 60 多条命令，每条查询都要带条件；漏一处就是串。SQLite 没有行级安全兜底 | 句柄只连着一个用户的文件，写错查询也读不到别人的 | 有行级安全兜底，但每个连接要设对当前用户 |
| 单机模式 | 多一列永远等于同一个值 | 就是「只有一个用户库」，表结构和现在一样 | 要求用户装数据库，违背「零依赖」 |
| 无运行时依赖 | 满足 | 满足 | 不满足：要引入驱动或自己写协议 |
| 现有 214 项测试 | 大部分要改 | 基本不动 | 全部要改 |
| 一个用户导出、删除 | 逐表按条件导 | 复制、删除一个文件 | 逐表按条件导 |
| 一个用户写得多 | 锁住所有人 | 只锁自己 | 互不影响 |
| 跨用户的统计 | 一条查询 | 要逐个库查，或另记到控制库 | 一条查询 |
| 升级表结构 | 一次 | 每个库各一次（打开时做） | 一次 |
| 多台应用服务器 | 不行 | 不行 | 行 |
| 4GB 机器上的开销 | 小 | 小（句柄按最近使用淘汰） | 数据库自己要占 1GB 左右 |

### 3.2 结论

**每个用户一个库。** 理由按重要性排：

1. 所有者最在意的是「不会串」。这种做法里，串数据需要打开错的文件，而打开文件只有一个入口（§3.3）；共用库里，串数据只需要任何一条查询少写一个条件。
2. 这个产品里用户之间没有任何共享（没有团队、协作、审批），所以没有跨用户的事务，也就用不上共用库的好处。
3. 单机模式和 SaaS 是同一套表、同一套代码，区别只是有几个库文件。
4. 量级（§1.1）远在单机 SQLite 的能力之内。

ADR-0004 §2.2 写的是「每条命令带着当前用户，查询和写入都按它过滤」。本篇把它改成「每条命令拿到当前用户的库」。对外的承诺不变，实现更难写错。

### 3.3 结构

```
<数据目录>/
  control.db                 用户、会话、邀请、设备、令牌、唤醒表、配额、跨用户审计
  tenants/<user_id>/vk.db    现在的全部业务表（账号组、账号、作品、成片、平台稿、任务、事件…）
```

- **唯一入口**：`core/tenancy.mjs` 的 `openTenant(userId)`。其他任何文件不得自己拼路径打开库（CI 检查，§10）。
- **命令上下文**：`executeCommand(ctx, name, args)`，`ctx = { userId, role, deviceId, origin, db }`。`db` 是当前用户库的句柄。`userId` 只能来自会话或设备令牌，**不能来自请求参数**；任何命令的参数里都没有「用户」。
- **句柄**：按最近使用保留 64 个，其余关闭；每个库 `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。
- **写入方只有一个进程**。云端是单进程，每个库同一时刻只有一个写事务。
- **调度不遍历所有库**：`control.db` 里有 `tenant_wakeup(user_id, next_due_at)`，每个用户库在排期、租约变化时更新自己那一行。调度器每一轮只打开到点的库。
- **单机模式**：`control.db` 里有一行隐含的用户，不登录；`tenants/` 下只有一个库。旧的单库文件在第一次启动时移进来。

### 3.4 表结构的规矩（对新表和改动的表生效）

- 主键用 ULID（按时间有序，离线也能生成）。时间一律是 UTC 毫秒整数。
- 新表用 `STRICT`。状态列带 `CHECK (state IN (...))`，和状态机的白名单同源生成，不手写两份。
- 外键全部声明，并在外键列上建索引。
- JSON 只放「宽松的、不参与查询条件」的内容（指标、平台特有的设置）。会被筛选、排序、唯一约束用到的，一律是列。
- 改表结构只做「先加后减」：一个版本只加列、加表，旧代码照常能跑；确认没有旧版本在用之后，下一个版本才删。因为发布机会比云端晚升级（§9）。
- 迁移有版本号（`PRAGMA user_version`），只前进。打开库时发现版本低，就先 `VACUUM INTO` 留一份，再在一个事务里升级；失败则这个用户进入只读，并报给运营，不影响别的用户。

#### 这一轮设计带来的表结构改动

**文案：通用 + 各平台单独改**（设计见 `docs/design/work.html` 的「改内容」）

```sql
-- 通用文案放在语言版本上：中文版的通用文案管小红书、抖音、视频号、B站；英文版的管 TikTok、YouTube
ALTER TABLE cut_version ADD COLUMN title TEXT;
ALTER TABLE cut_version ADD COLUMN body TEXT;
ALTER TABLE cut_version ADD COLUMN tags_json TEXT;                     -- 字符串数组
ALTER TABLE cut_version ADD COLUMN rev INTEGER NOT NULL DEFAULT 0;     -- 每次保存加 1，防两处同时改

-- 平台稿上按字段覆盖；NULL = 跟通用走
ALTER TABLE publish ADD COLUMN title_override TEXT;
ALTER TABLE publish ADD COLUMN body_override TEXT;
ALTER TABLE publish ADD COLUMN tags_override TEXT;
ALTER TABLE publish ADD COLUMN edited_fields TEXT;                     -- 人改过哪些字段；再次入库不覆盖这些
```

生效的文案只在一处计算：`effectiveCopy(publish)` = 平台稿自己的 ?? 语言版本的通用。发布、卡片、页面都调它。现有 `overrides_json` 里的标题、正文、话题迁到这三列，其余平台特有的设置（TikTok 的隐私级别等）留在 JSON 里。

**时间：现在发和预约发分开**

```sql
ALTER TABLE publish ADD COLUMN timing TEXT NOT NULL DEFAULT 'at' CHECK (timing IN ('now','at'));
ALTER TABLE publish ADD COLUMN suggested_at INTEGER;   -- 发布方案给的建议，只读，用来说「原定…」
-- scheduled_at 保留：timing='at' 时必须非空且在将来；timing='now' 时必须为空
```

- 「不能是过去的时间」只在 `timing='at'` 且用户**改了时间**时检查。只改文案的保存不带时间，也就不会因为时间报错。
- 建议时间过了而还没确认：读的时候按平台规则重新给出最近可用时间，并带上「原定…」；不要求用户去改一个已经过去的时间。
- 现在发还是预约发**只在确认时整批选**（`publish.confirm` 带 `timing`），编辑不改它（所有者 2026-11-18 定：没有混合状态）。现在发也要照样过每日上限、最小间隔、出口位置和登录状态，过不了就不发并说明原因。
- 一次保存是一条命令、一个事务：`cut.edit { versionId, rev, common?, platforms: [{ publishId, title?, body?, tags?, follow?: [字段], at? }] }`。`rev` 对不上就拒绝并说明「刚被别处改过」。现有 `publish.edit` 保留给飞书卡片和 CLI，内部走同一个函数。

**设备与出口位置**（在 `control.db`）

```sql
CREATE TABLE user (
  id TEXT PRIMARY KEY, email TEXT NOT NULL UNIQUE COLLATE NOCASE, name TEXT NOT NULL,
  password_hash TEXT NOT NULL, state TEXT NOT NULL CHECK (state IN ('active','disabled')),
  is_operator INTEGER NOT NULL DEFAULT 0, created_at INTEGER NOT NULL
) STRICT;
CREATE TABLE session (
  token_hash TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES user(id),
  created_at INTEGER NOT NULL, last_seen_at INTEGER NOT NULL, expires_at INTEGER NOT NULL
) STRICT;
CREATE TABLE device (
  id TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES user(id),
  role TEXT NOT NULL CHECK (role IN ('executor','maker')),
  name TEXT NOT NULL, os TEXT, app_version TEXT, protocol INTEGER NOT NULL,
  token_hash TEXT NOT NULL UNIQUE, revoked_at INTEGER,
  last_seen_at INTEGER, created_at INTEGER NOT NULL
) STRICT;
CREATE INDEX idx_device_user ON device(user_id);
CREATE TABLE device_link (                       -- 设备码配对，10 分钟过期，只能用一次
  user_code TEXT PRIMARY KEY, device_code_hash TEXT NOT NULL UNIQUE,
  role TEXT NOT NULL, name TEXT NOT NULL, os TEXT,
  approved_by TEXT REFERENCES user(id), expires_at INTEGER NOT NULL, used_at INTEGER
) STRICT;
CREATE TABLE device_egress (                     -- 每台发布机每条线路最近一次探测
  device_id TEXT NOT NULL REFERENCES device(id), route TEXT NOT NULL CHECK (route IN ('cn','overseas')),
  ip TEXT NOT NULL, country TEXT, region TEXT, city TEXT, network TEXT, is_datacenter INTEGER,
  observed_at INTEGER NOT NULL, PRIMARY KEY (device_id, route)
) STRICT;
```

用户库里：`account` 加 `executor_id`（绑定的发布机）、`home_country`、`home_city`（这个账号上一次登录成功时的出口位置，§8）。

### 3.5 什么时候换 PostgreSQL

出现下面任何一条，就开新的 ADR 评估，不提前换：

- 要两台以上应用服务器，或对外承诺了单机做不到的可用性。
- 活跃用户超过 2000，或单机的写入延迟 P99 超过 200ms。
- 产品要做用户之间的共享（团队、协作、审批），出现跨用户的事务。

换的代价可控：适配器和通道已经不能直接碰库（零后门律），SQL 都在 `core/store` 后面。

### 3.6 备份与恢复

- 每小时对有改动的库做 `VACUUM INTO` 快照，加密后传到对象存储；保留 7 天逐小时、30 天逐日。`control.db` 同样处理。
- 目标：最多丢 1 小时的数据，4 小时内恢复。恢复演练是验收项，不是文档项（§10）。
- 用户导出 = 自己的库 + 自己的文件清单；用户删除 = 删库、删对象存储前缀、删 `control.db` 里的行。两件事都在界面上做。

## 4. 文件（A3）

> **2026-11-22 暂缓**（§15 第 8 条）。先验证一台电脑上制作和发布；所有者自己分机时继续用 `packages/relay`。本节是以后多个用户要分机时的方案，现在不实现。

ADR-0003 §2.5 定的是「文件存 volc1」，实测 volc1 出口只有 0.11MB/s。多个用户之后这条路走不通，所以改成：

- **对象存储**（S3 兼容；云端放国外后厂商另选，§15 第 2 条）。键是 `u/<user_id>/<sha256>`。只在一个用户内部去重；跨用户去重会让人能探测「别人有没有这个文件」，不做。
- **直连**：制作机向云端要一个限时的上传地址，直接传到对象存储；发布机同理要下载地址。应用服务器只签名、记账，不过文件流量。签名用 `node:crypto` 自己算，不引入 SDK。
- **断点续传**：超过 16MB 用分片上传，每片独立重试；上传任务记在制作机本地，机器重启后接着传。
- **校验**：上传完成时云端核对大小和哈希后才算入库；发布机下载后先核对哈希再发布。
- **预取**：平台稿一确认，绑定的发布机就开始下载，不等到发布时间。到点文件还没到，按「出问题」处理并说明还要多久。
- **保留**：所有平台稿都终结后 7 天删除原片，封面和预览版长期保留。每个用户有容量上限，快满时在界面上提醒。
- **单机模式**：同一个接口的本地目录实现，没有对象存储也能用。

## 5. 人的登录（A4）

- 邮箱 + 密码。密码用 scrypt 存哈希。会话令牌只存哈希，放 HttpOnly、Secure、SameSite=Lax 的 cookie；改状态的请求校验 Origin。
- 登录失败按「账号」和「IP」分别限速，互不连累。
- 注册要邀请码。是否放开注册是服务端的一个开关，不是另一套代码。ADR-0004 §2.3 的「`vk user invite`」改成运营页上的按钮（命令仍然存在）。
- 找回密码走邮件；发邮件用 SMTP 中继，是配置不是依赖。
- 用户之间互相看不到。运营能看到的只有：用户列表、容量、设备数、健康状态；看不到作品内容的界面入口不做。

## 6. 设备的登录（A5）

发布机和 Claude 插件都是「设备」。配对过程里用户不输入任何东西：

1. 设备启动后向云端要一对码：给人看的短码（如 `KQ7M-2XPD`）和只有设备知道的长码。
2. 设备打开浏览器到 `…/link?code=KQ7M-2XPD`。用户已登录就直接看到「『书房的 Mac』想接入你的 versekit，作为发布机」，点「允许」。
3. 设备轮询拿到令牌。令牌写进系统的凭据存储，云端只存哈希。

规矩：

- 令牌绑定一个用户、一个角色、一台设备。请求属于哪个用户**只看令牌**。
- 角色限权：`maker`（制作机）只能入库、看自己的作品；`executor`（发布机）只能领绑定给它的任务、回报结果、上报登录状态和出口位置。派生自 `commands.mjs` 里每条命令的 `permission`。
- 短码 10 分钟过期、只能用一次；页面上写清设备名、系统、角色，防止被人诱导批准别人的设备。
- 在界面上可以给设备改名、断开。断开后令牌立刻失效；断开发布机前说明「绑在它上面的 N 个账号会发不了」。

## 7. 发布机（A6）

- **安装**：客户端安装包（§15 第 7 条）。测试阶段不签名：Mac 第一次打开要去「系统设置 → 隐私与安全性」点「仍要打开」，Windows 要在 SmartScreen 上点「更多信息 → 仍要运行」，安装页配图文说明。所有者自己和内测前几位也可以继续用 `install.sh`（`curl` 下载的文件不带隔离标记，不弹拦截）。装好后注册成后台服务。
- **装完自动配对**：安装结束自动打开浏览器到 §6 的页面。
- **领活**：出站 HTTPS 长轮询（ADR-0003 §2.3 不变）。
- **平台账号登录全在网页上**（修订 DESIGN-TODO 第 11 条）：
  - 扫码：发布机在后台打开登录页，把二维码传到云端，网页上直接显示；用户用手机扫。
  - 短信：网页上填手机号和验证码，转给发布机填进去。现有的 `account.login.start / verify / resend / cancel` 已经是这个形状。
  - 两种都不行的平台：「在发布机上打开登录窗口」，人坐到那台电脑前操作。
  - 二维码和验证码只经过云端转发，不落库；登录数据仍只在发布机上。
- **官方接口的应用凭证**（TikTok 的 client secret 等）：网页上填，直接送到发布机保存，云端不存。
- **出口位置**：见 §8。

## 8. 出口 IP 与位置（A9）

要回答的是「平台看到的我在哪」，所以探测要走和发布相同的路：

- 发布机用**账号的浏览器**访问两个只回显来源 IP 的地址：一个在国内（云端自己的域名），一个在海外。浏览器会跟随系统代理和分流规则，Node 的 `fetch` 不会，所以不能用后者代替。
- 两条线路的结果不一样（常见于分流代理）时，两条都显示：国内平台看到的是哪、海外平台看到的是哪。
- 位置和线路类型（家庭宽带 / 机房）在云端查离线 IP 库，不把用户的 IP 发给第三方。离线库查不到城市时只写国家，不猜。
- 每 10 分钟、以及每次发布前探测一次。
- **保护**：每个账号记住上一次登录成功时的国家和城市。发布前探测到的位置和它不在同一个国家时，这个账号的自动发布暂停，推一条「等你处理」：`继续用新位置` / `我去关掉代理`。这是把 D10「账号和手机同网」从靠人记变成代码保证。
  - 「继续用新位置」要再确认一次，并写出后果（平台会看到账号换了国家）；确认后才改基线、恢复发布。
  - 「我去关掉代理」不改任何东西，待办保留为「等发布机复查」；发布机下一次探测到位置回到基线才自动恢复。
  - 暂停期间确认照常能做，但确认面板要写明哪些平台暂停、要等位置处理完才会发；不能说「现在开始发」。
- **提醒（不暂停）**：线路是机房线路，或国内、海外两条线路出口不一致时，设备那一行用黄色标出「可能是代理」。同一个国家里的代理靠这个发现；它不自动暂停，因为分流代理是很多人的正常用法。
- **基线从哪一刻开始**：第一次登录成功时。所以接发布机、登录第一个账号的界面上要显示当时的 IP 和线路类型，并提醒先关代理；否则基线从第一天就是错的。
- 界面：侧栏底部一行，每一页都看得到（设计见 `docs/design/app.js` 的 `initShell`）。平时是灰字，位置变了才变黄。

## 9. Claude 接入：plugin，不是 skill（A7）

| 需要做到 | 单独的 skill | plugin |
|---|---|---|
| 教 Claude 怎么写各平台文案 | 能 | 能（plugin 里带技能） |
| 登录到用户自己的后台，并且记住 | 不能：没有凭据存储 | 能：敏感配置进系统的安全存储；持久目录 `${CLAUDE_PLUGIN_DATA}` |

| 不同用户不串 | 靠用户自己配对地址和令牌 | 令牌由 §6 的配对发下来，属于谁就进谁的库 |
| 升级 | 用户自己换文件 | 跟着 marketplace 更新 |

依据是 Claude Code 官方文档（2026-11-18 核对）：plugin 可以同时带技能、MCP 服务、hooks；`userConfig` 的 `sensitive` 值存进平台的安全存储；本机 MCP 服务随 plugin 启用启动。

**形状**

```
plugins/hifabu/
  .claude-plugin/plugin.json
  skills/versekit-ingest/SKILL.md      现有入库技能，改成调用工具而不是命令
  .mcp.json                            本机 stdio 服务：node ${CLAUDE_PLUGIN_ROOT}/server.mjs
  server.mjs                           薄的一层：工具由 commands.mjs 派生，传输是到云端的 HTTPS
```

- **工具**（由命令注册表派生，是第四端）：`work_add`（交清单）、`work_status`（上传到哪了）、`work_list`、`work_show`、`stats_works`（下一期能问上一期的数据）。只暴露 `maker` 角色允许的命令。
- **上传不阻塞会话**：`work_add` 校验清单、算哈希、登记上传任务后立刻返回任务号；实际上传由一个独立的后台进程做，状态写在 `${CLAUDE_PLUGIN_DATA}`，Claude Code 关了也接着传，下次打开还能查。
- **第一次用**：Claude 调任何工具时发现没有令牌，工具返回「需要接入」并打开浏览器到 §6 的页面；用户点「允许」后重试即可。
- **装 plugin**：系统页给一句话「把这句话发给 Claude」，Claude 自己完成安装。用户不需要知道命令。这默认用户的 Claude 是能装东西的那种（Claude Code、桌面版）；只用网页版的走不通，页面上要有一句分流（这一轮没画）。
- **通用文案谁来写**：入库清单里直接写的 `title / body / tags` 就是通用文案，以平台名为键的是该平台单独写的（现有清单格式不用改）。入库技能要改一句：能共用的就只写通用，只有确实要不一样的平台才单独写；否则通用文案管不了几个平台。
- **要实测的**（文档没写清）：`sensitive` 值在 macOS 上是否进钥匙串；本机 MCP 服务派生的后台进程在 Claude Code 退出后是否存活（不存活就改成由发布机的后台服务代传，或在下次启动时续传）。

claude.ai 网页版读不了本机文件，所以不在这一轮范围内。

## 11. 升级（A10）

- **云端**：运营发布。启动时先迁移到点的库，其余库在第一次打开时迁移。
- **协议版本**：设备每次请求带 `protocol`。云端同时支持当前和前一个版本；更旧的设备领不到活，界面上这台发布机显示「要更新才能继续发」和「现在更新」按钮。
- **发布机**：沿用 #217 的后台自动更新（空闲时更新、失败自动退回）。界面上能看到版本、能点「现在更新」、能关自动更新。
- **plugin**：跟着 marketplace；工具的参数只加不减。

## 12. 安全

| 威胁 | 对策 |
|---|---|
| 用户 A 读到用户 B 的数据 | §3.3 唯一入口 + 参数里没有用户 + 两用户遍历全部命令的测试（§13） |
| 令牌泄露 | 只存哈希；一台设备一个；界面上可断开；角色限权 |
| 诱导批准别人的设备 | 短码 10 分钟过期；页面写明设备名、系统、角色；只有主动发起配对的浏览器会被带到这个页面 |

| 云端被攻破 | 平台登录不在云端；应用凭证不在云端；备份加密。**作品、文案、成片在云端，服务方看得到**，要在用户协议里写明 |
| 文件串用户 | 键带用户前缀；签名地址只签自己前缀下的键；有测试 |

## 13. 架构验收（进 CI，也进每个实现单的口径）

新增门禁和测试，口径 id 见 `docs/design/ACCEPTANCE.md` 第十一节。

| 门禁 | 断言 |
|---|---|
| `check:tenant`（静态） | 只有 `core/tenancy.mjs` 打开库文件；命令的参数表里没有 `userId` / `user` |
| 隔离遍历（动态） | 建两个用户，各有账号组、作品、设备。用 A 的会话和 A 的两种设备令牌，把 `commands.mjs` 里**每一条**命令对着 B 的每种对象 id 调一遍，全部是「不存在」。命令表新增一条，这个测试自动多测一条 |
| `check:parity` | CLI、HTTP、卡片、MCP 四端的命令集合一致 |
| `check:no-cli-in-ui` | 页面里没有命令行 |
| 迁移 | 用上一个版本的库文件升级，升级前后跑同一组读命令，结果一致；升级失败只影响这一个库 |
| 先加后减 | 迁移脚本里出现 `DROP COLUMN` / `DROP TABLE` 时，必须能指出「上一个版本已经不读它」的提交 |
| 文件 | A 的签名地址取不到 B 的文件；哈希不对的上传不入库 |
| 协议兼容 | 上一个版本的发布机能对着新云端完成一次领取、回报 |
| 恢复演练 | 从备份恢复一个用户库，数据截至最近一次快照 |

**改了表结构、命令、鉴权、文件、设备的 PR**，描述里必须带这张检查表并逐条写结论：

1. 新的读写走的是 `ctx.db` 吗？有没有新开库的地方？
2. 新命令的 `permission` 是什么？制作机和发布机各能不能调？
3. 表结构改动是「先加」吗？旧版本的发布机还能跑吗？
4. 新列是列还是 JSON？为什么？有没有该建没建的索引？
5. 失败留现场了吗（`error_code` + 人话 + 事件）？
6. 界面上的新按钮对应哪条命令？

### 15.1 飞书怎么接多个用户

飞书的自建应用只能给建它的那个飞书组织用。所有者的应用给不了别的组织的人，除非上架成商店应用（要审核，对几个用户不值得）。所以：**每个用户用自己的飞书建一个只属于她的机器人**。现有实现已经有「扫码创建应用」的官方流程，用户不用手填任何凭证，这一步原样搬到多用户下。

- 入口在系统页「通知」分段：`接飞书` → 页面上出二维码 → 用飞书 App 扫 → 机器人建好 → 还差「让卡片上的按钮能点」这一步时，给一个按钮直接跳到飞书里开通 → 开通后自动发一张测试卡片。每一步的状态自己往下走，不用回来点「我弄好了」。
- 云端为每个接了飞书的用户维持一条长连接；卡片只发给这个用户自己，按钮回调带着的是这个用户的身份。包含在隔离遍历测试里：A 的卡片按钮动不了 B 的任何东西。
- 飞书应用的凭证存在控制库里，加密，密钥不在库里。它是通知通道的凭证，不是平台登录；平台登录仍然只在发布机上。
- 可以不接：状态是「不用飞书」，确认只在网页上做。红线不变：没有人确认，一条都不会发。
- 用户能选往飞书发哪几类：要你确认的、出了问题的、每天的结果。
- 卡片发不出去（机器人被停用、删除）：系统页和「今天」各有一条，要你确认的回到网页上，不静默。
- 用 Lark（海外版）的用户：接口域名不同，这一轮不做，接的时候按域名分开即可。

### 15.2 IP 位置库的选项

| 选项 | 给什么 | 许可证 | 要做的 | 问题 |
|---|---|---|---|---|
| **DB-IP City Lite** | 国家、省、城市 | CC BY 4.0 | 注明来源并链接到 db-ip.com；每月更新一次 | 城市精度一般，国内尤其；够用来判断「国家变没变」 |

| MaxMind GeoLite2 | 国家、城市、ASN | 自己的 EULA | 要注册账号和密钥；新版出来后 30 天内必须删掉旧版 | 条款最重，自托管的人每人都要自己注册 |
| ip2region | 国内到城市和运营商 | 代码是 Apache-2.0，数据来源混杂 | — | 仓库里自带的数据已经不更新；海外只到国家 |
| 商业库（IPinfo、DB-IP 付费版） | 城市更准、每天更新、能直接标出代理和机房 | 付费 | — | 现在的量不值得 |

**结论：DB-IP City Lite 加 IPinfo Lite。** 暂停发布只看「国家变没变」，两家在国家这一级都可靠；城市只用来显示；「可能是代理」靠 ASN 是不是机房来判断。两个库都是 MMDB 格式，自己写一个只读解析器（约 150 行），不引入依赖。库文件不进仓库，云端和单机模式都在第一次用到时下载、按月更新。界面上在系统页设备分段的底部写一行来源。城市显示不准是已知的，所以文案里位置只作参考，判断只用国家。
