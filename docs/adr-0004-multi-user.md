# ADR-0004：同一个服务上多个用户

**状态**：提议（2026-11-17）　**决策人**：产品 + Claude
**前置**：[ADR-0003](adr-0003-distributed.md)（云端 + 制作机 + 发布机）。本篇在它上面加用户层，不改它的派活、租约、文件方案。
**修订**：PRD「不做」里的「托管 SaaS、替别人保管账号」「团队、权限」两行；BLUEPRINT D11（部署形态）；ADR-0003 §2.7（鉴权）
**影响**：数据模型（所有者）、鉴权、Web 登录、飞书通道、设备令牌、系统页

---

## 1. 背景

所有者 2026-11-17 确认：

- versekit 不是只给自己一个人用。已经有 1 个内测用户，希望她**登录到所有者的服务**来用，不是各装各的。
- 顺序是先把所有者自己用顺，但设计和架构从现在起按多用户考虑。
- 所有者自己的制作机和发布机不是同一台，目前没法协同（入库只能在发布机上跑 `vk work add`）。这件事由 ADR-0003 解决，多用户建立在它之上。
- 内测用户有一台常开、和手机同网的电脑，可以当她自己的发布机。

不变的事实约束：平台账号只能在和手机同网的电脑上操作（11-14 小红书处罚的根因）。所以云端永远不能替任何用户发布。

## 2. 决策

### 2.1 托管的是控制面，不是平台登录

| 在云端（所有者的服务） | 在用户自己的发布机上 |
|---|---|
| 用户、作品、文案、排期、状态、数据、成片文件 | 平台的浏览器登录数据、官方接口的令牌和应用凭证 |

BLUEPRINT D6「凭证永不出用户机器」不变，并且是对用户的承诺：服务方拿不到任何平台的登录。PRD 的「不做托管 SaaS」改成「不托管平台登录」。

要对用户说清楚的另一面：她的作品、文案、排期和成片文件存在所有者的服务器上，服务方看得到。

### 2.2 所有数据都有所有者

- 新增 `user`。账号组、作品、平台账号、发布方案、设备、发布机、事件都直接或间接属于一个用户。
- 隔离做在 `core` 里：每条命令执行时带着「当前用户」，查询和写入都按它过滤。CLI、HTTP、飞书按钮都由 `commands.mjs` 派生，所以隔离只写一次（三端一致律）。适配器和通道不能绕过（零后门律）。
- 用户之间互相看不到任何东西。没有共享、协作、团队、审批；这些仍然不做。
- 单机模式保留：本机只有一个隐含的用户，不用登录，行为和现在一样。数据库里仍然有这一行 `user`，两种模式同一套表结构。

### 2.3 进来的方式：只能邀请

- 不开放注册。所有者用 `vk user invite <名字>` 生成一次性邀请链接（有过期时间），对应的 Web 入口只有所有者看得到。
- 被邀请的人打开链接，自己设密码。之后用名字和密码登录。
- 密码只存哈希（`node:crypto` 的 scrypt，不引入运行时依赖）。登录失败按账号和 IP 限速。会话用 HttpOnly cookie。
- 所有者可以停用一个用户：停用后不能登录，她的设备令牌全部失效，数据保留。
- 不做飞书登录：要求双方的飞书应用打通，对一两个用户不值得。

### 2.4 设备令牌属于用户

沿用 ADR-0003 §2.7 的「每台设备一个令牌、按角色限权」，加一条：令牌属于某个用户，只能进这个用户的空间。

| 设备 | 能做什么 |
|---|---|
| 制作机（Claude + 入库技能） | 入库、查看自己的作品 |
| 发布机 | 领取绑定给它的任务、回报结果、上报登录状态 |

用户在系统页上自己加设备、看设备、吊销设备。加发布机的流程：系统页生成一条一次性的接入命令，在那台电脑上跑一次。

### 2.5 飞书

每个用户用自己的飞书接收卡片和确认。**怎么接还没定**（见 §4）。在定下来之前，没有接飞书的用户只在 Web 上确认，红线不变：没有人确认，一条都不会发。

### 2.6 所有者自己先用

所有者是第一个用户：先用它把自己的制作机和发布机连起来，跑顺之后再邀请内测用户。内测用户进来之前，ADR-0003 §4 的验证计划要通过。

## 3. 后果

**得到**
- 内测用户不用自己搭服务，只装发布机。
- 所有者两台机器协同的问题一并解决。
- 数据模型一次到位，以后加用户不用翻表。

**付出**
- 公网 Web 要有登录、防爆破、会话管理；出了安全问题影响的是别人的数据。
- 所有者要对别人的数据负责：备份、升级不丢数据、服务挂了有人管。
- 每条命令、每个查询都要过一遍隔离，漏一处就是串数据。要有测试钉住：用户 A 的令牌和会话读不到、改不了用户 B 的任何东西。
- 自动更新（#217）在云端和发布机版本不一致时怎么办，要补规则。

**不变**
- 三条铁律、状态机、适配器契约、平台规则、发布前必须人确认。
- 凭证不离开发布机。

## 4. 还没定的

1. **飞书怎么接**：每个用户自己建飞书应用并填凭证，还是所有者的应用对外分发。前者简单但用户要多做一步。
2. **云端放哪**：ADR-0003 选的是 volc1（国内）。内测用户和她的发布机在哪、到 volc1 的速度如何，要实测。
3. **容量**：volc1 是 4GB 内存、40GB 硬盘，成片文件按 ADR-0003 的保留规则能放几个用户，要估算。
4. **用户协议**：替别人存内容之后，至少要有一页说明存了什么、没存什么、怎么导出和删除。

## 5. 要新设计的界面

| 界面 | 回答什么 |
|---|---|
| 登录 | 名字、密码；没有注册入口 |
| 接受邀请 | 设密码，然后告诉她下一步：接一台发布机 |
| 接入发布机 | 一条接入命令，接上之后在这一页看到它上线 |
| 系统页「发布机」 | 从「这台电脑」一行改成列表：哪台、在不在线、绑了哪些账号 |
| 系统页「设备」 | 制作机和发布机的令牌，可吊销 |
| 作品页为空 | 新用户的第一屏：怎么让 Claude 入库 |
| 所有者的用户管理 | 邀请、停用；只有所有者看得到 |

命名：「账号」继续指平台账号；人这一层叫「用户」，界面上直接用名字，不出现「账号」二字。

## 6. 验证计划（通过后改为「已定」）

1. 隔离：两个用户各有账号组、作品、设备；用 A 的会话和令牌遍历全部命令，读不到、改不了 B 的数据。
2. 邀请：链接只能用一次、会过期；停用用户后她的会话和令牌立刻失效。
3. 防爆破：连续输错密码被限速，不影响别的用户登录。
4. 单机模式：不登录、不带令牌，全部现有测试照常通过。
5. 所有者用它连起自己的制作机和发布机，完成一次「入库 → 确认 → 发布」。
