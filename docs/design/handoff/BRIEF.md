## 3. 结构

### 3.1 对象

**一次交付** = 一期 × 选定的一个成片版本 + 封面 + 通用文案（加上必要时按平台单独写的字段）。到发布机就是一个作品、一个成片，账号组里每个账号一条平台稿。

一期只交一个版本。要换版本就再交一次，发布机上**同一期更新，不新建**（见 §4 缺口 5）。

### 3.2 谁负责什么

| 环节 | 在哪 | 由谁 |
|---|---|---|
| 认出「这一期」是哪些文件 | 制作机，Claude 会话 | 技能按**项目交付约定**读（每个项目一份，vibe-video 和 tcm-video 各写各的） |
| 校验、算大小、估到达时间 | 制作机 | `vk`（新：`work.push` 的预览） |
| 上传、断点续传、断网重试 | 制作机后台服务 | `vk`（新：上传不占着会话） |
| 下载、入库、生成待确认稿 | 发布机 | 现有 |
| 发布前确认 | 发布机网页、飞书 | 现有，不变 |
| 状态回到制作机 | 中转 → 制作机 | `vk`（新：投递回报带平台稿摘要） |

### 3.3 状态词表（制作机这边看到的）

| 状态 | 说的是 | 用户看到 |
|---|---|---|
| 正在传 | 制作机 → 中转 | 「正在传 01 赌徒谬误：31 / 52MB，还要约 20 秒」 |
| 等发布机来取 | 在中转上，发布机还没开始下载 | 「已到中转。发布机上次来取是 3 分钟前」 |
| 发布机在下载 | 发布机 ← 中转 | 「发布机在下载：40%，还要约 5 分钟」 |
| 等你确认 | 已入库，平台稿已生成 | 「到了。3 条等你确认：小红书 11-25 20:00、抖音 11-25 21:00、B站 11-26 12:00」 |
| 没交成 | 任一步失败 | 原因 + 下一步怎么做（§5） |

「已发」「已排期」不在第一版里：这些由发布机和飞书说。制作机这边到「等你确认」为止。

## 4. 要补的 `vk` 能力（CLI 完整律：插件只能调用这些）

1. **预览**：`work.push` 加 `dryRun`。只校验，返回会传哪些文件、多大、按实测速度估多久到、哪些平台的文案会被拒，一个字节都不传。
2. **上传不占着会话**：`work.push` 登记任务后立刻返回投递号，由制作机的后台服务负责上传、续传、重试；关掉 Claude Code 也接着传。
3. **查投递**：`delivery.list` / `delivery.show <id>`。制作机向中转查状态（中转现有 `GET /v1/deliveries/:id` 两种 token 都能读）。
4. **回报带摘要**：发布机回报「已入库」时，带上作品 id、每条平台稿的平台、账号和建议时间，以及被拒的平台和原因。中转原样存，制作机读。中转同时记录「发布机最后一次来取的时间」。
5. **同一期是更新，不是新建**：现在发布机用 `inbox/<投递号>` 当来源，所以同一期交两次会出现两个作品。改成清单里的 `source`（制作机上那一期的路径）优先。
6. **默认账号组**：`relay.connect` 时记一个默认组，交付时不用每次说组名。
7. **到了就通知**：发布机入库后，在飞书和「今天」页上出一条：「新到 1 期：01 赌徒谬误，3 条等你确认」。如果已有这类通知就复用。

## 5. 出错时怎么说

| 情况 | 什么时候发现 | 说什么 | 不做什么 |
|---|---|---|---|
| 中转连不上 | 上传时 | 「中转连不上，已经排队。网通了会自动接着传，不用再说一遍」 | 不丢任务，不让人重来 |
| 发布机离线 | 在中转上等太久 | 「已到中转，但发布机 6 小时没来取。打开那台电脑上的 Hifabu 就会自动下载」 | 不改派到别的机器（账号绑发布机） |
| 文件大 | 预览时 | 超过 100MB 时说明「约要 28 分钟到发布机，后台传，不用等」 | 不设硬上限。中转剩余空间不到 2GB 会拒收，这时说「中转空间不够」并给出剩多少 |
| 文案缺某个平台，或超限 | 预览时 | 「小红书标题 24 字，限 20 字」，Claude 给出改短的版本 | 不默默截断 |
| 这一期没有发布文案 | 读目录时 | Claude 按选题和字幕起草一份，把草稿给人看一眼再交 | 不拿字幕时间轴当正文 |
| 版本拿不准 | 读目录时 | 「02 有三个版本，默认交最新的 v3」；「灵动版」这种不是版本号的，问一句 | — |
| 发布机上没有这个账号组 | 发布机入库时 | 投递失败，原因原样回到制作机：「发布机上没有账号组『南竹』」 | — |

## 6. 三个方案（详见 proposals.html）

- **A. 插件里一个技能，调用 `vk`（推荐）**：在 vibe-video 的会话里说一句就交。新东西最少，Claude 已经能跑 `vk`。
- **B. 插件带本机 MCP 服务**：工具是 `handoff_preview / handoff_send / handoff_status`，由命令注册表派生。结构化，不靠 Claude 拼命令。这是 ADR-0005 §9 以后 SaaS 要的形状；现在只有所有者一个人用，做它要多一轮。
- **C. 盯目录自动交**：渲染完放进「待交付」文件夹就自动交，不经过 Claude。最省事，但选错版本、文案没写时没人拦。

## 7. 所有者 2026-11-24 定的

1. **形态：方案 A**，插件里一个技能，调用 `vk`。B 留到给别人用时由同一组命令派生；C 不做。
2. **制作机这边**：素材齐全就直接交，只有猜过的地方才停下来问。
3. **水印**：交带水印的成片（`成片/` 里的）。
4. **「灵动版」这类不是版本号的变体**：每次问。

## 8. 和 Hifabu 账号的关系

插件和发布机都用 Hifabu 账号登录（[../account/BRIEF.md](../account/BRIEF.md)）。所以：

- §4 第 6 条「默认账号组」不变，但「送到哪台发布机」由账号决定：只有同一账号的发布机拉得到。
- 第一次说「交给发布机」而制作机还没登录时，先走登录（账号设计稿的「Claude 里」一页），登录完接着交，不用重说。
- 账号还没开通传片时，说明去哪申请，并记住这一期。
