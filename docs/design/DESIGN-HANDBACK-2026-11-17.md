## 三、ADR-0004（多用户）：先评审，不派工

所有者 2026-11-17 定的方向：已有 1 个内测用户，要她**登录到所有者的服务**来用。先把所有者自己用顺，但从现在起按多用户设计。

这和两处现有约定冲突，评审通过后要改：

- `docs/PRD.md`「不做」表里的「托管 SaaS、替别人保管账号」和「团队、权限」两行
- `docs/BLUEPRINT.md` D11（单机是默认）

所有者已经拍板的：

- 托管的是控制面，平台登录仍然不离开用户自己的发布机
- 只能邀请，不开放注册
- 邀请链接 + 自己设密码，不做飞书登录
- 内测用户有常开、和手机同网的电脑当发布机

还没定的（ADR §4），评审时要有结论：

1. 每个用户的飞书怎么接
2. 云端放哪；到内测用户发布机的速度要实测
3. volc1 的容量够几个用户
4. 用户协议：存了什么、怎么导出和删除

**依赖**：ADR-0004 建在 ADR-0003 上，ADR-0003 也还是「提议」。两篇要一起评审。所有者自己「制作机和发布机不是同一台、没法协同」的问题，由 ADR-0003 解决，不需要等多用户。

**建议的实现顺序**（评审通过后）：先给现有数据加「所有者」这一层（单机模式下是一个隐含用户，行为不变）→ ADR-0003 的云端和发布机 → 登录和邀请 → 所有者自己跑顺 → 邀请内测用户。第一步越早做越便宜。
