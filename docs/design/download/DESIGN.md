# 发布机下载页与安装器（2026-11-26，设计师）

插件重新设计 [../plugin/DESIGN.md](../plugin/DESIGN.md) §D 第 8 单的任务书和结构。状态：**所有者 2026-11-26 已确认**，三处待定都选推荐方案，原话「按照你的建议来」：
- A：测试期用锁定版本的一行安装脚本，不做未签名的 .pkg。
- B：在 hifabu.com 上镜像 Node、biliup、lark-cli，sha256 以上游为准。
- C：所有者那台发布机改为跟正式发版走。

所有者还同意：**新的更新逻辑上线之前，先在发布机系统页把自动更新关掉**。这样 main 上合进来的改动不会直接装到管真实账号的机器上。§6.2 的升级路径因此改为「发版后手动点一次『现在更新』」。

依据：所有者已定的「插件和发布机完全分开，发布机在 hifabu.com 单独下载」（11-26）、「做客户端、单机优先，测试期不签名」（11-22）、「界面上不出现命令行」（11-18，针对发布机）、改名计划 [../RENAME-HIFABU.md](../RENAME-HIFABU.md) §3「本机数据目录这次不搬」（11-26）。

现状（origin/main @ bbb84a9，读代码得出）：
- 安装：`curl -fsSL https://raw.githubusercontent.com/versekit-labs/versekit/main/install.sh | bash`。一次装上私有 Node、**main 分支最新代码**、biliup、lark-cli，再注册后台服务。Node、biliup、lark-cli 都按上游的校验和核对，**程序包本身默认不校验**（`VERSEKIT_APP_SHA256` 可选）。
- 自动更新（`packages/core/src/update.mjs`）：后台每 6 小时查一次 GitHub **main 最新提交**，有新的就下载 main 的源码包，用包里的 install.sh 升级，起不来再退回 `app.prev`。也就是说，**main 上每合并一张单，6 小时内所有发布机都会自动装上**，没有「发版」这一步。

## 0. 一页结论

1. **有「发版」这一步**：从 main 打 tag，用发布脚本做出一个**只含运行文件**的程序包，连同 `SHA256SUMS`、带锁定哈希的 `install.sh`、组件清单，一起放到 `hifabu.com/download/<版本>/`。版本目录**只增不改**。
2. **自动更新改成跟发版走**，不再跟 main 走。合并到 main 不等于推到所有人的发布机。
3. **安装包形态**：测试期不签名，所以用**锁定版本的安装脚本**（终端里粘贴一行），不用 .pkg。原因是：不签名的 .pkg 在新版 macOS 上要进「系统设置 → 隐私与安全性」点「仍要打开」，还要输管理员密码，比粘贴一行更难、更吓人。正式版有了签名和公证后，再出 .pkg（所有者已定）。
4. **核心只装两样**：私有 Node 和 Hifabu 程序，再注册 1 个后台服务。**B 站组件 biliup 在第一次添加 B 站账号时装，飞书组件 lark-cli 在第一次接飞书时装**，都在发布机网页上点按钮完成。
5. **第三方文件放到 hifabu.com 上做镜像**：Node、biliup、lark-cli 的文件和上游逐字节相同，sha256 写死在发版清单里。发布机在国内，直连 GitHub 和 nodejs.org 经常很慢（所有者已定：镜像）。
6. **所有者那台发布机先关自动更新，发版后点一次「现在更新」**：系统页的这个按钮还按旧逻辑取 main，会装上含新更新逻辑的版本；从那以后它跟发版走，再把自动更新打开。数据目录不动，后台服务名按改名 R5 换掉。

## 2. 安装包形态（问题 2）

| | A. 锁定版本的安装脚本（推荐，测试期） | B. 不签名的 .pkg | C. 现状：GitHub main 上的 install.sh |
|---|---|---|---|
| 用户怎么装 | 打开「终端」，粘贴一行，回车 | 下载、双击，被 macOS 拦下；到「系统设置 → 隐私与安全性」点「仍要打开」，输管理员密码，再走安装向导 | 打开「终端」，粘贴一行 |
| Gatekeeper | 用 curl 下载的文件不带隔离标记，不弹拦截（设计判断，第 P2 单要在 macOS 14、15 真机上各验一次） | 未签名、未公证，一定会被拦。较新的 macOS 去掉了「右键打开」这条绕过路径，只能去系统设置里放行（同上，要真机核实） | 同 A |

| 要不要管理员密码 | 不要（装在用户目录） | 放行和安装都要 | 不要 |
| 构建成本 | 已有 install.sh，改成「读锁定清单」即可 | 要 pkgbuild/productbuild，还要处理只装到当前用户的安装域 | — |

> **定（所有者 11-26）：A。**「不出现命令行」这条原本是针对发布机的网页，这里只在安装时粘贴一次，之后不再碰终端。B 不签名时，用户要多走一步「去系统设置放行 + 输密码」，看到的是「Apple 无法验证……是否包含恶意软件」，体验和安全形象都比 A 差。**正式版**（有了 Apple 开发者账号、能签名公证时）出 .pkg，做到完全不用终端，那时再单独开单。

页面上给的一行（例子，版本号随发版变）：

```
curl -fsSL https://hifabu.com/download/0.3.0/install.sh | bash
```

给内行的「先校验、再运行」（同一页，默认收起）：

```
curl -fsSLO https://hifabu.com/download/0.3.0/install.sh
echo "<install.sh 的 sha256>  install.sh" | shasum -a 256 -c
bash install.sh
```

评审批评的不是「curl | bash」这个形式本身，而是：不锁版本、不校验、一口气装一堆东西、悄悄注册服务。A 方案把这四点都改掉了：
- **锁版本**：地址里有版本号。
- **校验**：脚本里写死每个文件的 sha256。
- **少装**：核心只装 Node 和程序，组件用到才装。
- **先说再做**：注册服务之前先在终端里打印要注册什么。

## 3. 下载页 `hifabu.com/download`（问题 1）

### 3.1 页面结构（一页一个任务：装好发布机）

1. **标题和一句话**：「把这台电脑设成 Hifabu 发布机」。说明什么是发布机：装了 Hifabu、负责到点发布的那台电脑。
2. **放在哪台电脑上**（先于安装，最重要的一条）：发布机要和**你发布时用的手机在同一个网络**（同一个家里的宽带）。平台会把「手机和电脑不在一个地方」当成风险。这条来自 2026-11 小红书账号被处罚的教训（`docs/research/publish-risk.md`）。
3. **系统要求**：macOS 13.5 或更新（这是 Node 26 的最低要求，P2 单里核对）（Apple 芯片和 Intel 都行）；约 300MB 空间，另加放视频的空间；需要一直开机联网（合上盖子会暂停）。Linux 可以用，但只做了测试，不在页面上主推。Windows 不支持。
4. **安装**：一行命令，加复制按钮，写明「打开『终端』（在启动台里搜『终端』），粘贴，回车」，配一张终端截图。下面接一句：「装好后浏览器会自动打开发布机的控制台，在『系统』页登录你的 Hifabu 账号。」
5. **会装什么**（表格，每行一项，数据来自版本清单）：

   | 装什么 | 多大 | 从哪来 | 放在哪 |
   |---|---|---|---|
   | Node.js 运行时 26.x（官方原版） | 约 45MB | nodejs.org，hifabu.com 镜像 | `~/.versekit/node` |
   | Hifabu 程序 | 约 2MB | hifabu.com | `~/.versekit/app` |
   | B 站上传组件 biliup（**用到才装**） | 约 5MB | github.com/biliup/biliup-rs，hifabu.com 镜像 | `~/.versekit/bin` |
   | 飞书组件 lark-cli（**用到才装**） | 约 10MB | github.com/larksuite/cli，hifabu.com 镜像 | `~/.versekit/bin` |

   放在哪一列如实写 `~/.versekit`（这次不搬，RENAME §3）。目录搬家以后，这一列跟着清单变。
6. **会在后台常驻什么**：**1 个**后台服务 `com.hifabu.daemon`（改名 R5 之后的名字），开机自动启动，崩溃自动拉起。它负责：在本机 127.0.0.1 上提供控制台；每 5 分钟从 Hifabu 取新作品；到点发布**你确认过的**作品；每 6 小时检查一次有没有新版本，空闲时自动更新（可在系统页关掉）。日志放在哪也写上。除此之外，不改系统设置，不装浏览器插件，不要管理员密码。
7. **这个版本**：版本号、发布日期、更新了什么（来自 CHANGELOG）、`install.sh` 的 sha256、完整校验清单 `SHA256SUMS` 的链接、源码 tag 链接、「先校验再运行」三行（默认收起）。
8. **怎么卸载**：发布机控制台「系统 → 卸载 Hifabu」，默认保留数据（账号登录、作品），也可以选「连数据一起删」。同时列出数据目录的位置，方便手动删。最后提醒一句：卸载后到「我的 Hifabu」把这台机器移除。
9. **以前的版本**：一个链接，指向 `hifabu.com/download/versions/`，列出保留着的版本，给要退回的人用。

页头、页脚和官网其他四页一致，导航加一项「Download」。首页和「我的 Hifabu」都链到这一页。插件页**不**链到这里，只在「发布机没来取」时由 Claude 给出官网地址（插件设计 §A.8）。

### 3.2 写法

- 中英双语，和插件页一样：英文正文，下面一段中文。
- 不出现 VerseKit、vk（改名后用 `hifabu`）。路径里的 `.versekit` 如实写出，旁边注明「旧名，之后会改」。
- 版本号、大小、sha256 都由发布脚本生成，不手写。

## 4. 组件用到才装（问题 3）

### 4.1 能力（守 CLI 完整律）

`commands.mjs` 新增三条，CLI、HTTP、系统页按钮都从这里派生：
- `component.list`：列出组件，每个组件写明是否已装、装的版本、发版锁定的版本、大小、来源。
- `component.install <biliup|lark-cli>`：从发版清单里锁定的地址下载，按清单里的 sha256 校验，装到 `bin/`。
- `component.remove <名字>`。

### 4.2 什么时候触发，用户看到什么

| 组件 | 触发点 | 用户看到 |
|---|---|---|
| **biliup** | 在发布机「账号」页点「添加账号 → B 站」时，组件还没装 | 扫码之前先插一步：「B 站上传要用开源组件 biliup（约 5MB，来自 biliup-rs，版本 0.2.4）。」按钮「安装并继续」，点了显示进度，装完直接进入扫码。失败时说明原因，给「重试」。 |
| **lark-cli** | 在「系统」页点「接飞书」时，组件还没装 | 同样的一步：「接飞书要用飞书官方命令行组件（约 10MB，来自 larksuite/cli，版本 1.0.97）。」按钮「安装并继续」 |
| 兜底：biliup 被删了，又到了要发 B 站的时候 | 发布前检查 | 这一条不发，状态「出了问题」，`error_code: component_missing`，人话「B 站组件没装，到『系统 → 组件』装上后点重试」，留事件。不能悄悄跳过 |
| 兜底：飞书组件不在 | 推送卡片时 | 系统页「最近出的问题」里写一行，网页上的确认照常能用 |

- **已经装了的不动**：现有安装升级时，已装的组件按新版本锁定的版本升级；没装的不补装。所有者那台机器上 biliup 和 lark-cli 都已经在，升级后照常可用。
- **系统页「组件」一块**：列出两个组件的状态，有「安装」「移除」按钮，没有命令行。

## 5. 发版怎么做（问题 4）

### 5.1 版本号和 tag

- 程序版本用 `package.json` 的 `version`（语义化版本），发版时升号。tag 写成 `app-v0.3.0`，和插件的 tag 区分开。插件用 `claude plugin tag` 生成的 `hifabu--v0.2.0` 格式。
- 系统页和 `hifabu version` 显示 `0.3.0`。从 main 直接装的开发版继续显示 `0.3.0+<短提交号>`（ACC-update-06 的拼法不变）。

### 5.2 发布脚本 `deploy/hifabu/publish-release.mjs`

照插件发布脚本 `publish-plugin.mjs` 的做法：

1. 只能从一个干净的 tag 运行，工作区有改动就拒绝。
2. **打程序包**：`hifabu-app-0.3.0.tar.gz`，只放运行要用的东西（`packages/*/src`、`packages/web/public`、`bin`、`package.json`、`LICENSE`、`THIRD_PARTY_NOTICES.md`），用白名单打包。现在 GitHub 源码包有 47MB，里面 `.claude/` 和 `docs/` 都用不上（ACC-install-06 的实测）。要求打包可复现：同一个 tag 打两次，sha256 相同。
3. **组件清单** `manifest.json`：

   ```json
   {
     "schema": "hifabu.release/1",
     "version": "0.3.0",
     "commit": "<40 位>",
     "releasedAt": "2026-12-01",
     "app": { "url": "https://hifabu.com/download/0.3.0/hifabu-app-0.3.0.tar.gz", "sha256": "…", "size": 2100000 },
     "node": { "version": "v26.13.1", "files": { "darwin-arm64": { "url": "https://hifabu.com/download/deps/node-v26.13.1-darwin-arm64.tar.gz", "sha256": "…", "size": 0, "upstream": "https://nodejs.org/dist/v26.13.1/…" } } },
     "components": {
       "biliup": { "version": "v0.2.4", "files": { "darwin-arm64": { "url": "…", "sha256": "…", "size": 0, "upstream": "…" } } },
       "lark-cli": { "version": "1.0.97", "files": { "…": {} } }
     },
     "notes": "CHANGELOG 里这一版的内容"
   }
   ```

   上游文件的 sha256 由发布脚本**从上游校验和文件里取**（Node 用 SHASUMS256.txt，lark-cli 用 checksums.txt）。下载到镜像后再算一遍，两个一致才发布。biliup 上游没有校验和文件，发布脚本在两个不同网络各下载一次，结果一致才算数，并在清单里注明「来源：发布时计算」。
4. **生成 `install.sh`**：把 `manifest.json` 的内容写死进脚本，脚本运行时不再联网读清单。这样脚本自己的 sha256 就锁住了全部内容。
5. **`SHA256SUMS`**：版本目录里每个文件一行。
6. **上传**到 seoul-vps 的 `/var/www/hifabu/download/`：
   ```
   download/
   ├── latest.json              {"version":"0.3.0","manifest":"0.3.0/manifest.json","sha256":"<manifest 的 sha256>"}
   ├── versions/index.html      保留着的版本列表（脚本生成）
   ├── 0.3.0/                   install.sh  hifabu-app-0.3.0.tar.gz  manifest.json  SHA256SUMS  CHANGELOG.md
   └── deps/                    按文件名存的上游文件（多个版本共用，同名同内容，只增不改）
   ```
   版本目录和 `deps/` 里的文件**只增不改**，同名但内容不同时直接拒绝（照抄插件发布脚本的 `cmp` 检查）。`latest.json` 最后写入，用改名的方式原子替换。
7. `--dry-run` 只列出要上传的文件和 sha256，不连网。和插件一样，真正上传由协调器执行。

### 5.3 旧版本保留多久

- 程序包很小（约 2MB），**所有版本一直保留**，`versions/` 页列出来，方便退回。
- `deps/` 里的上游文件（每个 Node 包约 45MB）：只要还有一个保留的版本在引用就留着。没有版本再引用、又超过 90 天的，由发布脚本的 `--prune` 清理，清理前列出清单让协调器确认。
- 被撤回的版本（发现严重问题）：从 `latest.json` 里撤下，版本目录保留，在 `versions/` 页标「已撤回」，并写明原因。

> **定（所有者 11-26）：镜像。**发布机按要求和手机在同一个家庭网络里，也就是在国内，直连 github.com、nodejs.org 下载常常很慢甚至失败。镜像不影响完整性，sha256 仍然以上游为准。代价是 seoul-vps 每个 Node 版本多占约 200MB（四个平台），以及要核对三者的许可证是否允许再分发：Node 是 MIT；biliup-rs、lark-cli 在 P1 单里核对，不允许的就只记上游地址、不镜像。

### 5.4 谁来发、多久发一次

- 协调器发：一批改动合并、验收通过后发一版。至少每周一次，有紧急修复时随时发。发版前在临时 HOME 里用新的 install.sh 全新装一次，再从上一版升级一次，两次都通过才更新 `latest.json`。

## 6. 兼容和平滑升级（问题 5）

### 6.1 自动更新改成跟发版走

- `update.mjs` 改成读 `https://hifabu.com/download/latest.json`，不再读 GitHub 的 `commits/main`。有新版本时，下载那一版的 `install.sh`，**校验 `latest.json` 里给的 sha256**，再用它以非交互方式升级。空闲判断、60 秒自检、退回 `app.prev` 这些照旧（ACC-update-03、04 不变）。
- 系统页「更新了什么」改成显示 CHANGELOG 里这一版的内容，不再显示提交标题。
- 请求 hifabu.com 时不带任何个人信息，User-Agent 用固定的通用名（沿用 ACC-update-03 对 GitHub 的要求）。

> **定（所有者 11-26）：也跟发版走。**现在 main 上每合一张单，所有者的发布机 6 小时内就会自动装上，而它管的是真实账号。跟发版走以后，有问题的改动先在发版前的两次安装测试里被拦下。代价是：修好的东西要等发版才到。不留「跟 main 走」的通道。

### 6.2 所有者那台发布机怎么升级

0. **现在就做**（所有者已同意）：在发布机的「系统 → 发布机」里关掉自动更新。从此 main 上合进来的改动不会自动装到这台机器上。关掉期间，系统页仍能看到「有新版本」，只是不装。
1. **顺序**：先把第一个正式版本 `0.3.0` 发到 hifabu.com，**然后**才把「自动更新改读 hifabu.com」的代码（P3）和 main 上「转去装正式版」的 install.sh（P2）合进 main。
2. **演练**：在临时 HOME 里，用所有者机器数据的**副本**（不登录任何平台），装上所有者机器当前的版本，再模拟点「现在更新」走一遍升级。比对账号数、作品数、排期数、各平台登录状态文件，全部一致才往下走。
3. **所有者点一次「现在更新」**（协调器陪同，挑一个接下来 1 小时没有要发的时间）。这个按钮在旧版本里仍按旧逻辑走：取 main 的源码包，用包里的 `install.sh` 升级，同时设 `VERSEKIT_UPDATE=1`、通过 `VERSEKIT_APP_URL=file://…` 交出源码包，要求脚本保留 `app.prev`、不改 PATH、不开浏览器。main 上的 install.sh 改成「转去装正式版」以后（§6.3），**在这种情况下仍要遵守这套约定**，保证旧更新程序的自检和退回照常生效。P2 单要有这条测试。
4. 新版 install.sh 发现是在已有安装上升级时：
   - 安装目录照旧用 `~/.versekit`，数据目录不动（RENAME §3）。
   - 后台服务按改名 R5，从 `com.versekit.daemon` 换成 `com.hifabu.daemon`。
   - 已装的 biliup、lark-cli 按锁定版本升级，不删。
   - 写一行事件：「已改为从 hifabu.com 获取正式版本」。
5. **核对后重新打开自动更新**：系统页显示 `0.3.0`、后台服务只有 `com.hifabu.daemon`、一次到点发布照常执行之后，所有者在系统页把自动更新打开。从这时起，它只装正式发布的版本。

### 6.3 旧安装命令怎么办

- GitHub 上的 `raw.githubusercontent.com/versekit-labs/versekit/main/install.sh` 还会被旧文档和旧提示引用，**不能让它失效**。改法是：这个文件的 main 版本只做一件事，从 hifabu.com 读 `latest.json`，下载那一版的 install.sh，校验 sha256 后运行。运行前先打印一行「安装地址已改为 hifabu.com/download」。这样旧命令装到的也是正式版本，不再是 main 上的最新代码。
- `VERSEKIT_*` 这类覆盖用的环境变量，按改名 R4 的规则处理：新名字优先，旧名字作后备。
