# ADR-0002：把 social-auto-upload 作为可插拔发布后端

**状态**：提议（2026-11-14；11-15 按用户意见补 §4.4、§4.5、§5.5，改 §6、§8）　**决策人**：产品 + Claude　**修订**：ADR-0001 §4.2（SAU "只读逻辑"）、BLUEPRINT D1
**范围说明（2026-11-15）**：用户平台清单定为小红书、抖音、视频号、B站、TikTok、YouTube、官网、公众号。按 BLUEPRINT D9"官方接口优先"，SAU 只用于拿不到官方接口的平台（视频号；抖音在 #130 获批前），不再作为扩张平台数的手段。快手验证换成视频号或抖音。
**影响**：适配器层的范围、安装路径、`docs/platforms.md`、`docs/adapter-contract.md`、BLUEPRINT §1–§2、§6、§7、§9

---

## 1. 背景：ADR-0001 的前提变了

ADR-0001（2026-10-27）对 social-auto-upload（下称 SAU）的裁决是 **"只读逻辑，抖音例外"**，理由是 Python sidecar 的安装与故障成本高，而我们自己写 5 个平台"成本可控"。三周后的事实：

| 前提 | ADR-0001 时的估计 | 2026-11-14 实际 |
|---|---|---|
| 自研适配器进度 | 5 平台合计 5–7 天 | 3 个（B站 / TikTok / 小红书）；抖音、YouTube 未开工 |
| 小红书可用性 | 中高 | 真机账号 11-14 被处罚禁发（申诉后已恢复）；用户确认根因是开发机（英国）与手机（美国）同号异地使用、IP 来回跳，叠加短时间内多次自动发帖 |
| SAU 覆盖 | "抖音值得参考" | 17 个平台（视频 / 图文 / 文章），多数支持定时 |
| SAU 活跃度 | 未评估 | 16.5k star、2.8k fork，2026-10-22 仍在提交；主线已转向 `sau` CLI + 18 个 Agent Skill |

结论：**在"平台数量 × 持续跟改版"这件事上，我们一个人追不上一个有社区的项目。** 继续把适配器当护城河，会把有限时间耗在别人已经做完的事上。

## 2. 重新定位（与 BLUEPRINT §1.4 一致，不新增象限）

versekit 的差异化从来不是"能发几个平台"，而是 SAU 不做的那一层：

| versekit 独有 | SAU 现状 |
|---|---|
| 队列 / 租约 / 退避 / lane 串行 / 状态机 | 无（定时直接借平台原生定时） |
| 发布后数据回收与横向看板 | 无 |
| 账号健康主动发现（探测 + 被动信号 + 到期预测） | 只有手动 `check` |
| 飞书卡片：审批、重试、`private_then_public` 放行 | 无 |
| work × account 差异化编排 | 每平台单独一条命令 |

**新定位：versekit 是本地发布控制面；发布执行是可插拔后端。** 自研 CDP 适配器、SAU、官方 API 是并列的后端。

11-14 的处罚给这一层又加了一项 SAU 不做的事：**替用户守住账号安全**（§4.4）。

## 3. 许可证核查

| 对象 | 许可证 | 义务 |
|---|---|---|
| SAU 本体 | MIT（`Copyright (c) 2023 dreammis`） | 复制或修改其代码处保留版权声明与许可全文 |
| `utils/stealth.min.js` | MIT（puppeteer-extra 生成） | 同上，仅在移植它时 |

| patchright | 用户 pip 安装，我们不分发 | 若将来打包分发，先核实许可文本 |

ADR-0001 §2 的第 ① 闸（许可证）**通过**。（以上为对 MIT 的通常理解，不构成法律意见；商业分发前补齐 `THIRD_PARTY_NOTICES` 并复核。）

## 4. 决策

### 4.1 允许两种复用方式

| 方式 | 何时用 | 规则 |
|---|---|---|
| **A. sidecar 调用**（`adapter-sau`） | 我们没有自研适配器的平台 | 用户自行安装 SAU；versekit 只调用 `sau` CLI，**不打包、不 vendor**；SAU 是可选组件，不进入主安装路径 |
| **B. 带声明的移植** | 某平台需要升级为自研 CDP 适配器时（如抖音） | 文件头 `// ported from dreammis/social-auto-upload@<sha> <path>`；仓库根新增 `THIRD_PARTY_NOTICES.md` 收录 SAU 的 MIT 全文；照 ADR-0001 §6 剥离硬编码 |

**禁止**：直接 import SAU 的 Python 模块、修改用户本机的 SAU 安装、读写 SAU 的 `cookies/` 目录（见 §5.3）。

### 4.2 后端选择顺序

同一平台若两种后端都有，按 **自研 CDP > SAU** 选择，可在 `account` 级别覆盖。理由：自研后端满足全部 14 条硬规则（持久 profile、回读核实），SAU 后端在 §5 的几处是降级的。

### 4.3 修订 ADR-0001 与 BLUEPRINT D1

ADR-0001 §4.2 的裁决从"⚠️ 只读逻辑（例外：抖音参考）"改为"✅ 可作为 sidecar 后端；移植需带声明"。§4.2 列出的 sidecar 成本仍然成立，由 §4.1"可选组件、不进主安装路径"来限定影响面。

BLUEPRINT D1 原文"统一 Node，不做 Python sidecar"同步改为：**内核与自研后端统一 Node、零运行时依赖；Python sidecar 只以可选后端存在，不进主安装路径。** "用户侧多一个运行时就是灾难"的理由仍然成立，所以 SAU 只服务于用户主动选的平台，主路径（B站 / TikTok / 小红书 / YouTube）不需要 Python。

### 4.4 安全预算：控制面功能，对所有后端生效

换后端不会让风险消失：SAU 同样是浏览器自动化（patchright + stealth），平台看到的仍是程序在操作账号。11-14 的教训有两条，各对应一条约束：

| 约束 | 内容 | 由谁执行 |
|---|---|---|
| **每账号操作预算** | 每账号每天的发布、登录、体检次数有上限（PLAN R10），超出时任务排到次日并推事件，不静默丢弃 | 内核在**领取任务之前**检查，不依赖后端自觉；SAU 后端、自研后端、官方 API 一视同仁 |
| **执行环境同网** | 操作真实账号的机器，要和该账号日常使用（手机）在同一网络出口 | 文档约束 + 开发机保护：标记为开发机的实例拒绝对真实账号做登录、发布、体检、采集 |

具体数字（每平台、新旧账号是否区分）和"开发机"的判定方式在 PLAN 的里程碑 1 里定，不在本 ADR 里定。

这一层对外可以讲成卖点：**versekit 替你守住账号安全**——这是脚本类工具（包括 SAU）不做的。

### 4.5 回读确认是主路径，不是可选项

用户 11-14 否掉了"交给手机"模式，理由是每条都要手动操作。因此 L2 平台（§5.1）停在"待人工确认"不能作为常态：**每个经 SAU 接入的 L2 平台，都要配一个只读采集，回读作品列表，自动把 `notify_pending` 转为 `published`。** 人工点"我已发布"只是回读失败时的兜底。

只读采集比完整的发布适配器便宜得多（拦截作品列表接口即可），而且它本来就是数据回收需要的。一个 L2 平台没有回读之前，在 `platforms.md` 里标为"预览"，不计入对外宣称的平台数。

## 5. `adapter-sau` 设计约束（读过 SAU 源码后的硬事实）

### 5.1 结果输出不统一 → 必须分级

SAU 各平台的成功证据差异很大：

| 级别 | 平台（以 SAU@3847fff 为准） | SAU 给出的证据 | versekit 映射 |
|---|---|---|---|
| **L1 有结构化结果** | 知乎、大鱼号、雪球、Facebook、FB Page、Instagram | `--result` JSON，含 `published` / `scheduled` / `submission_unknown` / `failed` 等状态 | 按状态映射到 `published` / `failed`；`submission_unknown` → `notify_pending`（**禁止自动重试**） |
| **L2 只有退出码** | 抖音、快手、小红书、视频号、B站、百家号、微博、虎扑、支付宝、YouTube | `exit 0` + 打印一行 "upload submitted"；无作品 id / url | **不得直接记为 `published`**（违反硬规则 10、11）。先记 `notify_pending`，由该平台的只读采集回读作品列表、匹配到后自动转 `published`（§4.5，主路径）；回读超时或匹配不到才推卡片"请确认已发布"（复用现有 `publish.confirm`） |
| 非零退出 / 异常 | 全部 | traceback 或 stderr | 按 stderr 关键词归类到 `auth` / `asset_invalid` / `flaky_ui`，归不进去的为 `unknown`；**原文留进 run 现场**（反静默失败） |

这条决定了 `adapter-sau` 的天花板：**L2 平台的闭环靠"自动上传 + 回读确认"拼成，回读没写好之前就不是全自动。** 所以 §4.5 把回读列为接入 L2 平台的前提，UI 和文档里也要如实标出哪些平台还在"预览"。

### 5.2 契约 14 条的偏离清单

| 规则 | SAU 后端 | 处理 |
|---|---|---|
| 1 持久 Chrome profile | SAU 用 patchright + `storage_state` cookie JSON | 记为偏离；抖音、快手的 uploader 内部支持 `cdp_url` 但 CLI 未暴露——后续可向上游提 PR 暴露它，届时接入我们每账号的 Chrome |
| 10 / 11 结果判定与回读 | L2 平台无 | 见 §5.1 |
| 12 失败留现场 | 部分平台有截图 | 至少保留 stdout / stderr 全文 + 退出码 |
| 13 dry-run | 只有知乎有 `--prepare-only` | `adapter-sau` 的 dry-run = 参数校验 + `sau <p> check`，**不调用 upload**；文档注明它不产出发布前截图 |
| 2–9 | 属于 SAU 内部实现 | 不由我们保证 |

`capabilities` 如实声明：`publish: "cli"`，`collect: "none"`，`draft: false`（除非某平台在 SAU 里有草稿能力）。

### 5.3 凭证与零后门律

SAU 把 cookie 存在它安装目录下的 `cookies/<platform>_uploader/<account>.json`。
- versekit **不读、不写、不迁移**这些文件；账号的 `credential_ref` 只记录 `sau:<platform>:<account_alias>`。
- 登录走 `sau <p> login --account <alias>`，由用户在 SAU 弹出的窗口里扫码；`account.check` 调 `sau <p> check`，用退出码判断 `ok` / `expired`。
- 同一平台、同一账号不能同时挂在两个后端上（防串号）。

### 5.4 版本钉死

`adapter-sau` 的 `ready()` 检查 `sau` 是否在 PATH 上，以及 SAU 版本或 commit 是否在我们测过的白名单里；不在白名单时返回人话警告，不阻断。SAU 的 CLI 不承诺稳定，升级前先跑契约测试。

### 5.5 SAU 调用同样受安全预算约束

`adapter-sau` 的 `login` / `check` / `publish` 都是对真实账号的操作，和自研后端一样计入 §4.4 的每账号预算，一样受开发机保护拦截。SAU 自己建议的"两次发布间隔 > 30 秒"只是下限，不能替代每天的上限。

## 6. 后果

**得到**
- 平台覆盖从 3 个变成"3 个自研 + 最多 17 个 SAU"，不用自己追改版
- 精力回到控制面（采集、健康、手机决策），这才是 BLUEPRINT 定义的差异化
- 抖音不再需要"2–3 天从零写"

**付出**
- 用到 SAU 平台的用户要装 Python ≥3.10、`uv` 和 patchright 浏览器（约 150MB）；BLUEPRINT §1.2 的用户画像要算上这道门槛
- 故障面跨两种语言；每个 L2 平台都要额外写一个只读采集（§4.5）
- 安全预算会让"一次发很多条"变慢，这是有意的
- 依赖一个我们控制不了的上游：它可能改 CLI、停更，或改许可证（已发布版本的 MIT 不受影响）

**不变**
- 三条架构铁律，以及内核、命令表、事件模型
- B站 / TikTok 继续走自研后端
- **小红书**：自研后端，正常发布；**只在用户自己的电脑上执行**（与手机同网），受安全预算约束；开发机上的 agent 不碰真实账号（`docs/design/ACCEPTANCE.md` 真机红线）

## 7. 验证计划（通过才把状态改为"已定"）

前置：PLAN 里程碑 1（安全预算 + 开发机保护 + 试用脚本）已完成。

1. 选 **快手**（我们没有、SAU 支持 cdp_url、风控比抖音缓）做 `adapter-sau` 的最小实现：`ready` / `check` / `publish` / dry-run，只覆盖 upload-video
2. 契约测试：形状、`ready()` 语义、dry-run 不调用 upload、预算超限时不调用 `sau`（用假 `sau` 脚本跑）
3. 真机一次：**用户在自己的电脑上**（与手机同网）用快手测试号发一条"仅自己可见"，走完 `notify_pending → publish.confirm → published`；开发机上不做
4. 写进 `docs/platforms.md`：每个 SAU 平台标出 L1 / L2，以及"需安装 SAU"
5. 新增 `THIRD_PARTY_NOTICES.md`（进入移植方式 B 之前必须先有）

**时间盒 2 天。** 验证只证明"SAU 能当后端"；L2 的自动确认由下一个里程碑（回读确认）交付。如果连 SAU 的上传本身都不稳，就回退到 ADR-0001，只保留方式 B（带声明的移植）。

## 8. 未决问题

- ~~L2 平台的回读核实是否值得做~~ → 已定，进主路径（§4.5）。
- 是否向 SAU 上游提 PR：为 L2 平台统一加 `--result` JSON 输出、暴露 `--cdp-url`。对双方都有利，也能降低 §5 的偏离。
- SAU 的安装门槛和 G1"首次价值 < 30 分钟"的关系：SAU 平台是否计入 G1 的盲测。
- 抖音、快手、视频号的测试号由谁提供、在哪台电脑上登录（必须满足 §4.4 的同网约束）。
